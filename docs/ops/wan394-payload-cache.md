# 북 후보 payload 캐시 (WAN-394 §0)

격자 비용의 대부분은 **같은 후보를 다시 만드는 것**이다. 실측 분해:

| 이슈 | 총 시간 | 후보 생성 | 배치·재시뮬 |
| -- | -- | -- | -- |
| WAN-386 | 4시간 50분 | **4시간 40분** | 553초 |
| WAN-381 | 4시간 55분 | **압도적** | 몇 분 |
| WAN-389 | 2시간 48분 | **2시간 48분** | **6초** |

후보 집합은 좌표(종목·TF·창)와 탐지·진입 규칙만 정하고 **손절폭 가드·재진입 배치·복리와는
무관**한데, 격자를 돌 때마다 그 무거운 패스를 처음부터 다시 돌고 있었다. 이 캐시가 그것을
한 번만 하게 한다.

## 쓰는 법

측정 모듈이 `run_cells(..., payload_cache=PayloadCache())`를 **명시**해야 돈다. 안 주면
(기본) 캐시 코드를 한 줄도 타지 않고 예전과 **비트 단위로 같다**.

```python
from backtest.payload_cache import PayloadCache
payloads = run_cells(symbols, timeframes, ..., payload_cache=PayloadCache())
```

실행 시작에 **몇 칸이 히트/미스인지 먼저 찍는다**(WAN-335 관행 — 조용히 느려지면 「왜 안
끝나지」가 반복된다):

```
[payload-cache] backtest/cache/payloads (pay:b093ab2fb034): 히트 40칸 · 미스 8칸 — 미스만 계산합니다.
```

## 저장 위치·크기

`backtest/cache/payloads/<리비전>/<키>.pkl.gz` — 칸 하나가 파일 하나다(gzip 피클).
🚨 **DB에 넣지 않는다**(WAN-194: 6년치 시세와 같은 파일에 두지 않는다). `.gitignore`에 있다.

크기는 칸의 후보 수에 비례한다 — 15m 6년 칸이 가장 크고, 채택 좌표 48칸 한 판이 수백 MB
규모다. 확인:

```bash
uv run python -m backtest.payload_cache --stats
```

## 정리 — 자동 삭제는 없다

WAN-194/297 원칙: 무엇을 지웠는지 모르는 상태를 저장소가 스스로 만들지 않는다. 기본은
**세기**이고 삭제는 명시 플래그다.

```bash
uv run python -m backtest.payload_cache --prune-stale          # 세기만
uv run python -m backtest.payload_cache --prune-stale --apply  # 실제 삭제
```

`--prune-stale`은 **지금 리비전이 아닌** 디렉터리만 본다(현재 리비전은 건드리지 않는다).
기준이 하나도 없으면 거부한다.

## 🚨 왜 자동으로 무효화되나 — 이 캐시의 급소

엔진이 바뀌었는데 캐시가 히트하면 **「고쳤다고 믿으면서 옛 엔진 결과를 인용」**하게 된다
(WAN-364 소급 취소가 6년치 표를 통째로 얼린 그 부류이고, 캐시는 그것을 **자동화**한다).
그래서 키를 **손으로 나열하지 않는다**:

* **키는 `_Task` 그 자체다** — `wan169_leverage_book._Task`는 한 칸의 후보 생성을 완전히
  기술하는 frozen 데이터클래스라, *「payload를 바꾸는 것은 전부 `_Task`에 있다」*가 구조적으로
  참이다. `dataclasses.fields`를 훑으므로 **새 축이 생기면 자동으로 키에 들어간다**.
* 뒤집으면 **`_Task`에 없는 축은 키에 들어갈 수가 없다** — 손절폭 가드·`include_reentry`·
  복리는 배치 인자라 아예 없다. 즉 「가드·재진입 배치를 바꿔도 히트한다」는 규칙이 아니라
  **타입의 성질**이다.
* **소스 지문 두 겹**: `trade_store.engine_source_revision()`(엔진 정의 파일, WAN-253) +
  `payload_cache.RUNNER_SOURCE_FILES`(엔진 목록에 **없으면서** 후보를 만드는 러너 —
  `wan169_leverage_book.py`의 배선 · `wan228_reentry_census.py`의 재무장 파생).
* **직렬화 형식**이 바뀌면 `CACHE_SCHEMA_VERSION`이 무효화를 담당한다(`live/timeline_cache.py`
  와 같은 규약).

`tests/test_payload_cache.py`가 이 전부를 **동작으로** 건다 — 엔진 축을 하나 바꾸면 실제로
다시 계산하는지, 러너 파일 바이트를 바꾸면 리비전이 실제로 달라지는지.

## 익절 배수만 예외 — 부분집합이면 히트한다

`confirmation_multiples`(WAN-386 §0)는 `_Task`에 있지만 **키에서 뺀다**. 대신 파일이 어떤
배수를 담았는지 적어 두고 **요청 ⊆ 저장**일 때만 히트시켜 요청한 키만 남겨 돌려주고, 저장은
**합집합**이라 캐시가 쌓인다(배수 하나를 더 재려고 4시간을 다시 쓰지 않는다).

근거는 `derive_arm_candidates`가 배수마다 **독립으로** 청산을 낸다는 성질이고, 테스트가 그
독립성(`「1.5R만 요청」 ≡ 「넷 중 1.5R」`)을 동작으로 건다. 🚨 요청한 배수가 하나라도 모자라면
**미스**다 — 부분만 채워 돌려주면 격자에 구멍이 뚫린 채 「캐시 히트」로 보고된다.

## 안 하는 것

* ❌ 기본으로 켜지 않는다(옵트인).
* ❌ 배치 산출물(북 집계·거래)은 담지 않는다 — 담는 것은 **후보**뿐이다.
* ❌ 미스를 조용히 메우지 않는다.
* ❌ 자동 삭제·자동 정리 없음.
