# 당일 거래별 타임라인 백테 캐시 · 야간 크론 런북 (WAN-239)

`alphablock trades`(당일 KST 거래별 타임라인, WAN-234)의 **백테 대조**는 27칸(9종목 ×
15m·1h·4h) × 120일 워밍업이라 조회 순간에 계산하면 무겁다. 그래서 **야간에 미리 계산해
캐시에 담고, 조회는 캐시만 읽는다**(사용자 결정 2026-08-03). 이 문서는 그 야간 적재를
크론에 거는 방법이다. 라이브 부분은 장부 즉시 조회라 가벼우므로 캐시 대상이 아니다.

> ⚠️ **크론 등록은 사람이 한 번 한다.** 코드는 크론을 자동 등록하지 않는다(WAN-195 선례 —
> 러너/크론 자동 등록 금지). 아래 명령을 crontab/systemd timer에 **직접** 넣는다.

## 무엇이 도는가

```bash
# 전일(KST) 하루치 백테 타임라인 27칸을 계산해 캐시에 적재만 하고 종료.
uv run python -m cli.main trades --day <어제-YYYY-MM-DD> --persist-cache --jobs 8
```

- `--persist-cache`: 계산 후 **저장만** 한다(표를 렌더하지 않는다). 러너와 별개 프로세스다.
- 재적재는 **기본 거부**(같은 지문의 셀이 이미 있으면 건너뜀) — 크론이 두 번 돌아도 무해하다.
  엔진(코드)이 바뀌면 지문 해시가 달라져 **새 셀로 따로 적재**되고 옛 셀은 남는다(이력 보존).
  같은 엔진에서 강제로 다시 계산하려면 `--persist-replace`.
- `--jobs N`: (심볼, TF) 단위 병렬 워커 수. 결과는 직렬과 비트 동일(성능 노브일 뿐).
- 캐시·장부는 같은 DB 파일(`settings.db_path`, 기본 `data/ohlcv.db`)의 새 테이블
  (`timeline_cache_cells`/`timeline_cache_rows`)에 담긴다 — `alphablock trades`와 대시보드
  타임라인 탭이 같은 파일을 읽는다.

## KST 날짜 경계 (WAN-172)

"전일"·크론 시각·캐시 키의 날짜는 **KST**다. 저장·계산·비교는 UTC(epoch ms) 그대로다.
크론은 KST 자정 이후(예: **매일 00:30 KST**)에 전일을 적재한다. "어제(KST)" 계산 예:

```bash
YESTERDAY=$(TZ=Asia/Seoul date -d 'yesterday' +%F)   # GNU date(리눅스 서버)
# macOS(BSD date): YESTERDAY=$(TZ=Asia/Seoul date -v-1d +%F)
```

## 크론 등록 예시 (사람이 1회)

서버 시간대가 UTC여도 문제없다 — 아래는 명령 안에서 `TZ=Asia/Seoul`로 KST 날짜를 잡는다.
**KST 00:30 = UTC 15:30**이므로 crontab(서버가 UTC라고 가정)은:

```cron
# 매일 KST 00:30(= UTC 15:30) — 전일(KST) 하루치 백테 타임라인 캐시 적재
30 15 * * *  cd /path/to/AlphaBlock && /usr/bin/env TZ=Asia/Seoul bash -lc 'uv run python -m cli.main trades --day "$(TZ=Asia/Seoul date -d yesterday +%F)" --persist-cache --jobs 8' >> /var/log/alphablock/timeline-cache.log 2>&1
```

- 서버 시간대가 이미 KST면 `30 15`를 `30 0`으로 바꾼다.
- 로그 디렉터리(`/var/log/alphablock/`)는 미리 만들어 둔다(`mkdir -p`).
- 백테 격자는 서버(1GB 박스)에서 OOM 위험이 있다(WAN-174 런북) — 이 캐시 적재는 **하루치
  1일 창**이라 6년 격자보다 훨씬 가볍지만, 메모리가 빠듯하면 `--jobs`를 낮추거나 맥에서
  돌려 캐시 DB를 서버로 동기화한다.

## 실측 소요 시간 (완료 기준 5)

로컬 맥(Apple Silicon, `--jobs 8`) 기준, DB에 데이터가 있는 하루:

| 범위 | 셀 | 벽시계 |
| -- | -- | -- |
| 1종목 × 1h | 1 | ~2.7s (임포트·DB 오픈 오버헤드 포함) |
| 1종목 × 15m | 1 | ~2.7s |
| **전체 27칸(9종목 × 15m·1h·4h)** | **27** | **~15s** (CPU ~60s, 8워커) |

- 6년 측정 격자(셀당 ~37분, `intrabar_live` 밴드 비용)와 달리 이 캐시는 **하루 창 + 120일
  워밍업**이라 셀당 초 단위다 — 야간 크론에 충분히 가볍다.
- 서버(오라클 무료 티어 x86 1 OCPU)는 코어가 적어 더 걸리지만, 27칸 × 초 단위라 분 단위를
  넘지 않을 것으로 본다(서버 실측은 등록 후 로그로 확인).

## 조회(캐시만 읽음)

```bash
uv run python -m cli.main trades --day 2026-07-20          # 캐시를 읽어 즉시 뜬다
uv run python -m cli.main trades --day 2026-07-20 --recompute  # 캐시 무시, 즉시 재계산(무겁다)
uv run python -m cli.main trades --day 2026-07-20 --no-backtest # 라이브만
```

- 기본 조회는 **캐시만** 읽고, 미스면 무거운 계산으로 **폴백하지 않는다** — "🚨 백테 대조
  아직 계산 안 됨(야간 크론 대기 또는 `--persist-cache`로 적재, 즉시 보려면 `--recompute`)"을
  명시한다. 사용자가 원한 "클릭 시 재계산 금지"를 지키는 규약이다.
- 화면·터미널에 **엔진 배지**가 뜬다: (Ⅰ) 설명형 이름 + (Ⅱ) git 짧은 해시. 예:
  `오프셋2bp · 라이브밴드 · 게이트없음 · 필터1.28 · 1.5R · 롱온리 · 단일포지션 (59112dd)`.
  이름은 손으로 짓지 않고 **실제 파라미터에서** 뽑으므로 엔진이 바뀌면 이름도 저절로 바뀐다.
  더러운 워킹트리에서 적재하면 해시에 `-dirty`가 붙는다(그 셀은 다음 커밋 후 미스가 된다).
- 대시보드 「거래 타임라인」 탭도 같은 규약이다: 기본은 캐시를 읽고, "캐시 무시하고 즉시
  재계산" 체크박스가 온디맨드 재계산이다.

## 운영 메모

- 캐시는 **엔진 리비전에 종속**이다 — 코드를 배포(커밋)하면 그날 이후 조회는 새 해시를
  찾으므로, **배포 후 그날 크론이 돌기 전까지는 과거 날짜가 캐시 미스**로 보일 수 있다(옛
  해시 셀은 남아 있지만 조회는 지금 해시만 꺼낸다). 필요하면 해당 날짜를 `--persist-cache`로
  수동 재적재하거나 `--recompute`로 즉시 본다.
- 캐시 DB가 커지면(하루 27셀 × 여러 리비전) 오래된 리비전 셀을 정리할 수 있으나, 자동
  삭제는 두지 않았다(WAN-194 `doctor`가 자동 VACUUM을 두지 않은 것과 같은 이유 — 무엇을
  지웠는지 모르는 DB를 저장소가 스스로 만들지 않는다). 필요 시 사람이 정리한다.
