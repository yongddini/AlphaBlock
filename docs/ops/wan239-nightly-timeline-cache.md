# 당일 거래별 타임라인 백테 캐시 · 야간 크론 런북 (WAN-239 · WAN-297)

`alphablock trades`(당일 KST 거래별 타임라인, WAN-234)의 **백테 대조**는 채택 좌표 전 칸
(지금 48셀 = 12종목 × 15m·1h·2h·4h — WAN-252/307) × 120일 워밍업이라 조회 순간에 계산하면
무겁다. 그래서 **야간에 미리 계산해 캐시에 담고, 조회는 캐시만 읽는다**(사용자 결정 2026-08-03). 이 문서는 그 야간 적재를
크론에 거는 방법이다. 라이브 부분은 장부 즉시 조회라 가벼우므로 캐시 대상이 아니다.

> ⚠️ **크론 등록은 사람이 한 번 한다.** 코드는 크론을 자동 등록하지 않는다(WAN-195 선례 —
> 러너/크론 자동 등록 금지). 아래 명령을 crontab/systemd timer에 **직접** 넣는다.

## 무엇이 도는가

```bash
# 전일(KST) 하루치 백테 타임라인 전 칸(채택 좌표)을 계산해 캐시에 적재만 하고 종료.
uv run python -m cli.main trades --day <어제-YYYY-MM-DD> --persist-cache --jobs 8
```

- `--persist-cache`: 계산 후 **저장만** 한다(표를 렌더하지 않는다). 러너와 별개 프로세스다.
- 재적재는 **기본 거부**(같은 지문의 셀이 이미 있으면 건너뜀) — 크론이 두 번 돌아도 무해하다.
  엔진(코드)이 바뀌면 지문 해시가 달라져 **새 셀로 따로 적재**되고 옛 셀은 남는다(이력 보존).
  같은 엔진에서 강제로 다시 계산하려면 `--persist-replace`.
- `--jobs N`: (심볼, TF) 단위 병렬 워커 수. 결과는 직렬과 비트 동일(성능 노브일 뿐).
- `--days N`(WAN-297): `--day`에서 **거슬러** N일치를 한 번에 적재한다(기본 1 = 그날만 —
  기존 크론 줄은 동작이 그대로다). 오래된 날부터 채우므로 중간에 멈춰도 앞쪽이 이어진다.
  배포 뒤 되채우기가 이 플래그의 존재 이유다(아래 「배포 뒤」 절).
- 📌 **담기는 것은 셋업 전부다(WAN-297)** — 청산 거래만이 아니라 **미진입·미체결·건너뜀**
  까지(WAN-295 3열 대조가 읽는 행). 대시보드 「채택 좌표 전부」 모드가 이 캐시를 읽고,
  `alphablock trades` 표는 그중 **청산 행만** 싣는다(둘이 비트 동일함은 회귀 테스트가 고정).
- 캐시·장부는 같은 DB 파일(`settings.db_path`, 기본 `data/ohlcv.db`)의 새 테이블
  (`timeline_cache_cells`/`timeline_cache_rows`)에 담긴다 — `alphablock trades`와 대시보드
  타임라인 탭이 같은 파일을 읽는다.

## KST 날짜 경계 (WAN-172)

"전일"·크론 시각·캐시 키의 날짜는 **KST**다. 저장·계산·비교는 UTC(epoch ms) 그대로다.
크론은 KST 자정 이후(예: **매일 00:30 KST**)에 전일을 적재한다. "어제(KST)" 계산 예:

```bash
YESTERDAY=$(TZ=Asia/Seoul date -d 'yesterday' +%F)   # GNU date(리눅스 서버)
# macOS(BSD date): YESTERDAY=$(TZ=Asia/Seoul date -v-1d +%F)
```

## 크론 등록 예시 (사람이 1회)

서버 시간대가 UTC여도 문제없다 — 아래는 명령 안에서 `TZ=Asia/Seoul`로 KST 날짜를 잡는다.
**KST 00:30 = UTC 15:30**이므로 crontab(서버가 UTC라고 가정)은:

```cron
# 매일 KST 00:30(= UTC 15:30) — 전일(KST) 하루치 백테 타임라인 캐시 적재
30 15 * * *  cd /path/to/AlphaBlock && /usr/bin/env TZ=Asia/Seoul bash -lc 'uv run python -m cli.main trades --day "$(TZ=Asia/Seoul date -d yesterday +%F)" --persist-cache --jobs 8' >> /var/log/alphablock/timeline-cache.log 2>&1
```

- **먼저 서버 시간대를 확인한다**: `date` (또는 `timedatectl`). 두 경우를 다 적어 뒀으므로
  읽는 사람이 골라야 한다 — 지금 서버는 **KST**다(사용자 확인 2026-08-17).
- 서버 시간대가 이미 KST면 `30 15`를 `30 0`으로 바꾼다.
- 로그 디렉터리(`/var/log/alphablock/`)는 미리 만들어 둔다(`mkdir -p`).
- 백테 격자는 서버(1GB 박스)에서 OOM 위험이 있다(WAN-174 런북) — 이 캐시 적재는 **하루치
  1일 창**이라 6년 격자보다 훨씬 가볍지만, 메모리가 빠듯하면 `--jobs`를 낮추거나 맥에서
  돌려 캐시 DB를 서버로 동기화한다.

## 실측 소요 시간 (완료 기준 5)

로컬 맥(Apple Silicon, `--jobs 8`) 기준, DB에 데이터가 있는 하루:

| 범위 | 셀 | 벽시계 |
| -- | -- | -- |
| 1종목 × 1h | 1 | ~2.7s (임포트·DB 오픈 오버헤드 포함) |
| 1종목 × 15m | 1 | ~2.7s |
| **전체 27칸(9종목 × 15m·1h·4h)** | **27** | **~15s** (CPU ~60s, 8워커) |

> ⚠️ 위 표는 **좌표가 9종목 × 3TF이던 시절 실측**이다(2026-08-03). 지금 좌표는 48셀
> (12종목 × 15m·1h·2h·4h — WAN-252/307)이라 셀 수가 1.8배이고, 15m 칸이 늘어 셀당 비용도
> 더 든다. 새 실측은 서버 크론 로그로 확인할 것 — 옛 숫자를 현재 소요로 인용하지 말 것.

**§0 실측(2026-08-17, 12종목 · 4TF · WAN-313 벡터화 후)**: 화면 버튼과 같은 경로
(`backtest_setup_by_cell`, **직렬 `jobs=1`**)로 로컬 맥(M1)에서 잰 48셀 cold **~71초**
(2026-07-20, 12종목 전부 데이터 있는 날 · 셋업 100행 · 거래 있는 셀 26개). 화면 버튼이
직렬이라 이 값이 사용자가 실제로 기다리는 시간이다.

- ⚠️ **위 표의 `--jobs 8` 값과 나란히 읽지 말 것** — 자가 다르다(직렬 vs 8워커).
- ⚠️ **데이터가 있는 날로 재야 한다** — 같은 자로 2026-08-12/14를 재면 53~56초가 나오는데,
  그건 로컬 DB에서 12종목 중 3종목(ADA·DOT·BCH)만 그 날짜를 덮고 있어 나머지 45셀이 빈
  시장 데이터로 일찍 빠지기 때문이다. **빠른 게 아니라 덜 계산한 것**이다.
- ⚠️ **서버 값이 아니다**(로컬 M1). 서버 실측은 크론 로그로 확인할 것 — 다른 머신·다른
  모듈의 셀 비용을 옮겨 적는 것이 이 저장소가 반복해 당한 사고다(WAN-203→312, WAN-194 서버).

- 6년 측정 격자(셀당 ~37분, `intrabar_live` 밴드 비용)와 달리 이 캐시는 **하루 창 + 120일
  워밍업**이라 셀당 초 단위다 — 야간 크론에 충분히 가볍다.
- 서버(오라클 무료 티어 x86 1 OCPU)는 코어가 적어 더 걸리지만, 전 칸 × 초 단위라 분 단위를
  넘지 않을 것으로 본다(서버 실측은 등록 후 로그로 확인).

## 조회(캐시만 읽음)

```bash
uv run python -m cli.main trades --day 2026-07-20          # 캐시를 읽어 즉시 뜬다
uv run python -m cli.main trades --day 2026-07-20 --recompute  # 캐시 무시, 즉시 재계산(무겁다)
uv run python -m cli.main trades --day 2026-07-20 --no-backtest # 라이브만
```

- 기본 조회는 **캐시만** 읽고, 미스면 무거운 계산으로 **폴백하지 않는다** — "🚨 백테 대조
  아직 계산 안 됨(야간 크론 대기 또는 `--persist-cache`로 적재, 즉시 보려면 `--recompute`)"을
  명시한다. 사용자가 원한 "클릭 시 재계산 금지"를 지키는 규약이다.
- 화면·터미널에 **엔진 배지**가 뜬다: (Ⅰ) 설명형 이름 + (Ⅱ) git 짧은 해시. 예:
  `오프셋2bp · 라이브밴드 · 게이트없음 · 필터1.28 · 1.5R · 롱온리 · 단일포지션 (59112dd)`.
  이름은 손으로 짓지 않고 **실제 파라미터에서** 뽑으므로 엔진이 바뀌면 이름도 저절로 바뀐다.
  더러운 워킹트리에서 적재하면 해시에 `-dirty`가 붙는다(그 셀은 다음 커밋 후 미스가 된다).
- 대시보드 「거래 타임라인」 탭도 같은 규약이다: 기본은 캐시를 읽고, "캐시 무시하고 즉시
  재계산" 체크박스가 온디맨드 재계산이다.

## 🚨 배포 뒤에는 과거 날짜를 다시 돌려야 한다 (WAN-318 §5)

**엔진 소스가 바뀌면 과거 캐시가 전부 미스된다.** 캐시 키에 엔진 소스 지문
(`backtest.trade_store.engine_source_revision()` = `ENGINE_SOURCE_FILES` 내용 해시)이 들어가
있어서다. 크론은 **어제 하루치만** 돌므로, 배포 뒤에는 **필요한 날짜를 사람이 되채운다** —
안 그러면 대시보드·CLI가 그 날짜들을 계속 「캐시 미스 · 실행 버튼을 누르세요」로 띄운다.

실제로 그랬다(2026-08-17): 크론은 08-14·15·16을 **전부 적재 성공**으로 찍었는데, 09:47에
`backtest/leverage_book.py`를 건드린 커밋(WAN-312/PR #263)이 배포되면서 지문이 바뀌어 그
사흘이 통째로 미스가 됐다. **버그가 아니라 설계대로다** — 파라미터만으로 키를 만들면 엔진을
고쳐도 옛 결과를 꺼내 주기 때문에(WAN-106) 리비전을 키에 넣었고, 그 범위는 이미 「엔진 소스
파일만」으로 좁혀져 있다(WAN-253 — 문서·PM 커밋에는 안 흔들린다).

```bash
# 배포 뒤, 화면에서 보려는 날짜만큼 되채운다(WAN-297: 한 줄로 N일치 · 서버에서).
cd ~/AlphaBlock
uv run -- alphablock trades --day "$(TZ=Asia/Seoul date +%F)" --persist-cache --days 7 --jobs 2
```

`--days N`은 `--day`에서 **거슬러** N일치를 **오래된 날부터** 적재한다(중간에 멈춰도 앞쪽이
이어진다). 하루씩 돌리던 옛 `for` 루프와 결과는 같고, 손으로 날짜를 나열하지 않아도 된다.

- **되채우기 전에 지금 지문을 확인**하면 헛돌지 않는다: `uv run -- alphablock trades --day
  <날짜>` 가 미스라고 하면 되채울 날짜다(엔진 배지의 짧은 해시가 지금 지문이다).
- 서버는 1GB 박스라 `--jobs`를 낮게(2 안팎) 잡는다. 48셀이라 옛 27칸 시절보다 더 든다.
- ⚠️ **옛 셀은 지우지 않는다** — 새 지문으로 **추가**될 뿐이라 캐시 테이블이 커진다. 정리는
  아래 「캐시 정리」 절의 **명시적 옵트인**이다(자동 삭제 없음).
- ⚠️ **지문 정의를 바꿔 「미스가 안 나게」 하는 것은 해법이 아니다** — 그건 「엔진을 고쳤는데
  옛 결과를 꺼내 주는」 사고(WAN-106/253이 막은 것)를 되돌린다. 고칠 것은 **되채우는 절차**다.

## 운영 메모

- 캐시는 **엔진 리비전에 종속**이다 — 위 「배포 뒤」 절이 그 회복 절차다. 필요하면 해당
  날짜를 `--persist-cache`로 수동 재적재하거나 `--recompute`로 즉시 본다(옛 해시 셀은 남아
  있지만 조회는 지금 해시만 꺼낸다).
- 📌 **대시보드 「채택 좌표 전부」 모드도 이제 디스크 캐시를 읽는다(WAN-297 §1)** — 크론이
  채워 두면 **버튼 없이** 3열 대조가 뜨고, 버튼을 누르면 계산 결과가 곧바로 디스크에
  적재된다(다음 접속엔 버튼이 필요 없다). ⚠️ 옛 판은 세션 상태만 봐서, 크론이 48셀을 잘
  넣어 두어도 앱 재시작·새 브라우저 세션이면 무조건 버튼을 다시 요구했다(2026-08-15 사용자
  보고) — **그 화면은 캐시 미스가 아니라 세션-전용 계층 때문이었다.** 지금은 미스일 때만
  버튼 안내가 뜬다.
- 두 모드가 **같은 캐시**를 읽는다 — 「라이브 칸만」은 그날 라이브가 있던 셀만, 「채택 좌표
  전부」는 48셀 전부를 조회할 뿐 저장소는 하나다. 크론이 채택 좌표 전부를 채우므로 전자는
  자동으로 함께 채워진다.

## 캐시 정리 (pruning) — 명시적 옵트인 (WAN-297 §2-6)

캐시 DB는 **리비전마다 새 셀이 쌓여** 커진다(옛 셀은 안 지워진다 — 이력 보존). 정리는
**사람이 명시적으로** 한다. 자동 삭제·자동 VACUUM은 두지 않았다(WAN-194 `doctor`와 같은
이유 — 무엇을 지웠는지 모르는 DB를 저장소가 스스로 만들지 않는다).

```bash
# ① 먼저 세어 본다(읽기 전용) — 옛 엔진 리비전 셀이 기본 기준이다.
uv run -- alphablock trades --prune-cache

# ② 날짜 기준을 더한다(합집합): 옛 리비전 + 2026-07-01 이전 날짜
uv run -- alphablock trades --prune-cache --prune-before 2026-07-01

# ③ 실제로 지운다(파괴적 · 명시 옵트인)
uv run -- alphablock trades --prune-cache --prune-before 2026-07-01 --prune-apply
```

- `--prune-cache`만 주면 **세기만** 한다(리비전별 셀 수를 찍는다). 삭제는 `--prune-apply`.
- 기준이 하나도 없으면(`--prune-keep-all-revisions`로 리비전 기준을 뺐고 `--prune-before`도
  안 준 경우) **종료 코드 2로 거부**한다 — 기준 없는 일괄 삭제는 하지 않는다.
- ⚠️ **지운 뒤 파일이 줄지는 않는다** — VACUUM은 DB 독점 락이라 자동으로 걸지 않는다.
  줄이려면 러너를 멈추고 사람이 판단해 돌린다(WAN-194 원칙).
- ⚠️ **되채울 계획 없이 최근 날짜를 지우지 말 것** — 조회는 미스로 떨어지고 자동 재계산은
  하지 않으므로, 화면이 다시 버튼을 요구한다.
