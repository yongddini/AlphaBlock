# WAN-292 — 신규 3종목(DOGE·LINK·LTC) 펀딩비 백필 (상장~현재)

**날짜**: 2026-08-12 · **상태**: 데이터 적재 완료(로컬 `data/ohlcv.db`) + 일회성 백필
CLI 신설 · **기본값·토대 불변** · **실거래 보류 유지**(`ALPHABLOCK_LIVE_TRADING=false`)

## 0. 요약

사용자 지시("백필해") 실행. 옛 WAN-178(같은 백필, 롱-온리 시절 "펀딩 영향 작다"로
취소)이 아카이브돼 새 이슈로 대체됐다. DOGE·LINK·LTC 무기한선물 펀딩 레이트를 **상장
시점부터 현재까지** 백필해 `data.FundingRateStore`(`funding_rate` 테이블)에 적재하고,
`backtest.run` 격자의 `funding_coverage`가 9종목 전부 채워짐을 확인했다.

- **데이터 적재이지 배선 변경이 아니다** — 펀딩 배선은 WAN-91이 이미 뚫었고
  (`default_backtest_config`가 `funding_enabled`, 호출부가 `funding_rates` 전달),
  `apply_funding_proxy`(wan180)는 **자기 펀딩 데이터가 있으면 대리로 안 덮는다**. 즉
  백필이 들어오면 WAN-180/288의 BTC 대리가 **저절로 꺼진다** — 코드 배선 손댈 것 없음.
- **기본값·토대 불변**(`ConfluenceParams()`/`OrderBlockParams()`/`LeverageBookParams()`
  전부 그대로). 신규 3종목 채택 승격은 별도 결정 이슈(사용자).

  상장 시점부터 반환하므로 「상장~현재」가 그대로 채워진다.
- **coverage 99.99%**(LINK·LTC)는 각 심볼의 실제 보유 구간 `[first, last+8h)`에서 8시간
  간격 결측(구멍) 여부를 잰 값이다 — 6~7천 정산 중 한둘의 거래소측 결측(정상 범위).
- 📌 **신규 3종목이 오히려 기존 6종목보다 창이 넓다** — 기존 6종목은 옛 백필 시작점
  `2021-07-01`에 바닥이 걸려 있고 마지막이 `2026-07-22`(라이브 수집이 그 이후로는 안 붙은

  측정 창(2020-09-15~2026-07-22) 안에서 신규 3종목은 이제 **빠짐없이** 덮인다(기존 6종목은
  2020-09-15~2021-07-01 구간이 여전히 비어 있으나 이는 이 이슈 범위 밖 · 옛 백필의 성질).

## 2. `backtest.run` 격자 커버리지 (완료 기준 ②)

`uv run python -m backtest.run --positions single --symbol <9종목> --tf 4h
--start 2024-06-01 --end 2024-09-01 --format csv` 실측: **9종목 전부 `funding_coverage=1.0`**
(백필 전 DOGE·LINK·LTC는 "펀딩 0건" → coverage 0.0이었다). 로그도 세 신규 종목이 "펀딩
276건"으로 붙는 것을 보인다.

## 3. 도구 — 일회성 백필 CLI (`data.funding`)

`data/funding.py main()`에 `argparse`를 얹어 **서버 운영·일회성 백필** 경로를 신설했다.
**인자 없이 실행하면 예전과 완전히 동일**(백필 + 지속 최신화 루프, `run_funding_refresh`).

```bash
# 상장~현재를 한 번만 백필하고 커버리지 표 출력 후 종료
uv run python -m data.funding --backfill-only \
    --symbols DOGE/USDT:USDT,LINK/USDT:USDT,LTC/USDT:USDT --start 2019-06-01
```

- 📌 **`backfill_funding_all`이 아니라 `run_backfill_once`를 쓴다** — 전자는 저장된 마지막
  확정값 **다음부터** 이어받으므로(재시작 재개) **과거 구멍을 못 메운다**. 서버 정본 DB엔
  라이브 수집분(2026-06-24~)이 이미 있을 수 있어, 그 앞선 상장~2026-06-24 과거 구간이 바로
  메워야 할 구멍이다. `run_backfill_once`는 각 심볼을 `start_ms`부터 **통째로** 페이징하고,
  겹치는 라이브 수집 행은 **기본키(symbol, funding_time) UPSERT로 자연히 중복 제거**된다
  (중복 적재 금지 요건 충족).
- 회귀 테스트가 라벨이 아니라 **동작**으로 고정한다(`tests/test_funding.py`): start_ms부터
  전 구간을 채우는지(재개 아님) · UPSERT 중복 제거 · 커버리지 표 렌더 · `--backfill-only`
  CLI가 실제로 적재·출력하는지(네트워크 주입).

## 4. 서버 정본 DB 반영 (운영 메모)

로컬 `data/ohlcv.db`는 적재를 마쳤고 이 문서의 표가 그 실측이다. **서버 DB가 정본**이므로
(로컬은 SSH 없음 · 배선상 재현), 서버에서도 동일 명령을 한 번 돌리면 된다 — UPSERT라
라이브 수집분과 **중복·충돌 없이** 과거 구간만 채워진다. `funding_rate`는 git 비추적
(`ohlcv.db` gitignore)이라 PR은 **CLI·테스트·이 문서**를 싣고 데이터는 실행으로 재현한다.

  확인(대리 자동 해제). 그전까지 WAN-288의 신규 3종목 숏 수치는 **낙관 상한**으로 읽는다.
