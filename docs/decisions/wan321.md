# WAN-321 — doctor 경보가 두 겹으로 안 통한다: 거짓 경보 + 전송 실패

**결정일** 2026-08-17 · **범위** 운영/알림 전용 · **전략·엔진·토대 불변**

WAN-320 서버 확인 중 `systemctl --failed`에 doctor 두 유닛이 모두 `failed`로 떠 있었다.
DB는 멀쩡했고 **경보 쪽이 두 군데 고장나 있었다**: ① `open_positions` 0행이 매시간 거짓
경보를 냈고, ② 그 경고의 텔레그램 전송이 Markdown 파싱 실패로 나가지 않았다.

📌 **이 이슈는 「무엇을 보는가」를 건드리지 않는다** — 점검 항목은 WAN-194 소관이다. 고친
것은 **그 결과를 종료 코드·알림으로 어떻게 옮기는가**뿐이다.

---

## §1 장부의 성격을 갈랐다 — 누적 vs 현재 상태

**채택: 이슈가 「본질에 가장 가깝다」로 꼽은 세 번째 안.** `LEDGER_TABLES`가 성격이 다른 두
부류를 한 규칙으로 묶고 있었다.

| 상수 | 테이블 | 0행의 뜻 | 종료 코드 |
| -- | -- | -- | -- |
| `CUMULATIVE_LEDGER_TABLES` | `live_limit_orders` · `live_runner_sessions` · `paper_trades` | **이상** — 한 번 쓰면 지워지지 않는다 | 반영 |
| `STATE_LEDGER_TABLES` | `open_positions` | **정상** — 포지션은 닫힌다 | 반영 안 함 |

`LEDGER_TABLES`는 이제 **두 집합에서 파생**된다(`tuple(sorted(...))`). 새 장부를 추가하면서
성격을 안 고르면 분류가 비므로, 회귀 테스트가 「분류는 전체를 덮는다」를 동작으로 고정한다.

### 왜 이것이 안전한가 — WAN-194의 사고는 두 겹으로 그대로 잡힌다

WAN-194가 겪은 모양은 「체결은 `filled`인데 `open_positions`·`paper_trades`가 0」이었다.
새 규칙에서도 **두 갈래가 각각 독립적으로 종료 코드 1을 낸다**:

1. **`paper_trades`가 0** → 누적 장부라 그대로 걸린다(`empty_cumulative_ledgers`).
2. **「`filled` + 처분 NULL」** → `orphan_fills`가 잡는다. WAN-194 본문이 **이것이 진짜
   유실의 고유 서명**이라고 못 박았고, 그 열(`entry_status`)을 넣은 것이 바로 WAN-194다.

즉 정밀한 자(`orphan_fills`)와 옛 어림자(빈 장부)가 함께 걸려 있었고 **어림자만 울고
있었다**. 어림자에서 상태 장부 하나만 뺐다.

📌 **`empty_ledgers` 속성은 일부러 없앴다.** 그 이름은 상태 장부까지 포함해 「비면 경고」로
읽히므로, 호출부(`cli.main`·`dashboard.app`)가 옛 뜻을 조용히 이어받으면 거짓 경보가 그대로
돌아온다. 이름을 남기는 대신 `empty_cumulative_ledgers`(종료 코드) ·
`empty_state_ledgers`(정보)로 갈라 **성격을 고르도록 강제**했다 — 이 저장소가 반복해서 데인
「라벨과 동작이 어긋남」(WAN-91/95/112/123/159)의 예방이다.

### 왜 고쳐야 했나

싼 판이 1시간마다 도므로 이 거짓 경보는 **하루 24번** 울렸다. `systemctl --failed`가 상시
빨간 상태면 진짜 이상이 났을 때 구분되지 않는다 — WAN-194의 「실패가 성공과 같은 모양」 ·
WAN-318 §3의 「정상 정지가 failed로 보임」의 **거울상**이고, 이번엔 「정상이 실패로 보임」이다.

리포트에는 계속 찍는다. 다만 `⚠️ 빈 장부`가 아니라 **`ℹ️ 0행 = 열린 포지션 없음(정상)`**
정보 한 줄이고, 인구조사 표의 비고도 「페이퍼 장부(누적)」/「페이퍼 장부(현재 상태)」로 갈린다.

## §2 텔레그램 — 평문 전송 + 서식 실패 시 평문 1회 재전송

### 무엇이 깨졌나

`common/telegram.py`의 `send_message`는 기본 `parse_mode="Markdown"`(레거시)인데, doctor
경고문에 실리는 것이 하필 **테이블·열 이름**이다. `open_positions`의 밑줄이 「닫히지 않은
이탤릭」으로 읽혀 텔레그램이 400으로 거부했다:

```
status=400 description=Bad Request: can't parse entities:
Can't find end of the entity starting at byte offset 80
```

🚨 **WAN-185가 설계한 감시는 「`systemctl --failed` + 텔레그램」 두 다리인데 그중 하나가
죽어 있었다** — 즉 진짜 DB 손상이 났어도 폰에는 아무것도 가지 않았다. 그리고 그 실패는
`WARNING` 한 줄이라 **「경보를 못 보냈다」는 사실 자체가 경보되지 않았다.**

### 고친 것 — 두 겹

1. **doctor 경고문은 서식을 아예 쓰지 않는다**(`cli.main._doctor_alert_text`가 평문을 만들고
   `_notify_doctor_failure`가 `parse_mode=None`으로 보낸다). 알림은 읽히기만 하면 되므로
   표현력을 버렸다. 회귀 테스트가 `` ` ``·`*`가 **없는지**로 고정한다.
2. **클라이언트가 서식 파싱 실패(400)만은 평문으로 딱 한 번 다시 보낸다.** 이게 일반 해법이라
   **호출부를 안 고쳐도 모든 알림 경로가 함께 낫는다**.

**루프가 되지 않는다**: 평문에는 파싱 자체가 없어 같은 이유로 다시 실패할 수 없고, 재전송은
1회로 못 박혀 있다(회귀 테스트가 「평문 재전송이 또 실패해도 다시 시도하지 않는다」로 고정).
서식과 무관한 400(`chat not found`)·네트워크 소진(API가 답한 적 없음)은 **재전송하지 않는다**
— 평문으로 바꿔도 안 낫는 실패라 시도가 낭비이고, 후자는 서식 문제인지 판정할 근거조차 없다.

3. **전송 실패가 조용히 묻히지 않는다** — 클라이언트의 최종 실패 로그가 `WARNING` → `ERROR`
   로 올라갔고, `_notify_doctor_failure`는 실패 시 **경고 본문을 함께** `ERROR`로 남긴다
   (로그만 보고도 무슨 이상이었는지 알 수 있다). ⚠️ **종료 코드는 건드리지 않았다** —
   doctor의 종료 코드는 DB 무결성 판정 전용이고(이미 이상이라 1이다), 전송 실패로 그 뜻을
   흐리면 감시가 두 가지를 구분하지 못한다.

### 📌 범위 확인 (완료기준 5) — doctor 하나만의 문제가 아니었다

**모든 텔레그램 경로가 레거시 Markdown이고, 하나같이 자유 텍스트를 그 안에 끼워 넣는다.**
아래는 실측 조사 결과다:

| 경로 | 서식 안에 들어가는 자유 텍스트 | 위험 |
| -- | -- | -- |
| `cli.main` (doctor) | 테이블·열 이름(`open_positions`) | 🚨 **실제로 터졌다** |
| `data/repair.py:445` | `{s.error}` = 예외 메시지 | 🚨 높음(예외 문구는 통제 불가) |
| `data/collector.py:57` | `{event.reason}` = 복구 사유 | 🚨 높음 |
| `live/zone_limit_notifier.py:175` | 거부 사유 — `REJECT_CODE_*` 계열은 `min_stop_distance`처럼 **밑줄을 포함** | 🚨 높음 |
| `live/health_watch.py` | 심볼·TF(백틱)·복구 제목 `{prev.title}` | 중간 |

**그래서 고친 자리를 클라이언트로 잡았다.** 호출부마다 이스케이프를 다는 안(MarkdownV2)은
표현력이 남지만 **이스케이프 누락이 같은 사고를 다시 낸다** — 다섯 경로에 각각 정확히 달아야
하고, 새 경로가 생길 때마다 다시 틀릴 수 있다. 평문 폴백은 **틀려도 도착한다**.

⚠️ **폴백은 그물이지 면허가 아니다** — 폴백이 걸리면 그 알림은 서식 없이 도착하고 `WARNING`이
남는다. 위 표의 경로들을 평문으로 옮길지는 별도 판단이고, 이 이슈는 **경보가 도착하게** 하는
데까지만 한다.
