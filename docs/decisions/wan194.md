# WAN-194 — 체결은 났는데 포지션이 없다: 원인은 「처분 미기록」이었다

**날짜**: 2026-07-26 · **상태**: §3 닫음(코드) · §1·§2·§4·§5는 **서버 실행 대기**(개발
세션에 서버 접근이 없다) · **기본값·토대 불변** · **실거래 보류 유지**
(`ALPHABLOCK_LIVE_TRADING=false`)

## 1. 무엇이 문제였나

사용자 질문: *"LINK 기준 25일 23시에 생성된 오더블록이 26일 6시 15분에 다시 닿았는데 왜
이건 안 사진 거야?"* PM 실측 결과 `live_limit_orders`에는 `status=filled`(LINK 15m,
`fill_price=8.3586714`)가 있는데 `open_positions`·`paper_trades`가 0행이었다. 같은 DB에
SQLite `.recover` 산출 테이블 `lost_and_found`(283만 행)가 얹혀 있어 **DB 손상·복구로
매매 장부가 유실됐다**는 가설로 이슈가 열렸다.

📌 **그런데 「체결됐는데 포지션이 없다」는 손상의 증거가 아니다 — 정상 동작에서도 나오는
모양이다.** 지정가 체결과 페이퍼 진입은 **다른 사건**이고, 그 사이에 집행 계층
(`ExecutionEngine.on_entry`)의 거부 관문 넷이 있다:

| 거부 사유 | 조건 |
| -- | -- |
| `사이징 수량 0 — 진입 스킵` | 손절 거리 < `min_stop_distance_fraction`(**0.3%**, WAN-79) 또는 명목 상한 소진 |
| `이미 오픈 포지션이 있어 진입 스킵` | 같은 (심볼, TF)에 포지션이 있다 |
| `손절 참조가가 없어 사이징 불가` | `stop_price is None` |
| 리스크 한도 | `RiskManager.can_enter`가 막는다 |

**백테스트도 같은 자로 거부한다**(`zone_limit_backtest._to_trade`가 `qty <= 0`이면
후보를 버리고 슬롯도 잡지 않는다). 그래서 **거부 자체는 버그가 아니고 파리티도 깨지지
않는다.**

🚨 **버그는 그 거부가 아무 곳에도 안 남았다는 것이다.** WAN-194 이전 거부된 체결은:

* DB: `status='filled'`만 남고 포지션·거래는 없다 → **손상과 글자 그대로 같은 모양**
* 텔레그램: `handle_fill`이 `if not report.accepted: return` — **조용히 반환**
* 로그: INFO 한 줄(`거부(...)`)이 전부 — 서버 로그를 뒤져야 보인다
* `fill_report`: 체결로 세어 **체결률 분자에 그대로 들어간다**(거래가 안 됐는데)

즉 사고의 본체는 매매 기록 유실이 아니라 **관측 불가**였다. 사용자가 "왜 안 사졌지"를
물었을 때 장부가 답을 갖고 있지 않았고, 그래서 DB 손상 의심으로 반나절이 갔다.

## 2. 고친 것 (§3)

### 2-1. 체결의 하류 처분을 장부에 남긴다

`live_limit_orders`에 두 열을 더했다(`live/order_journal.py`):

* `entry_status` — `entered` | `rejected` | **NULL**
* `entry_reject_reason` — 거부 사유 문자열(사유를 안 주면 `"사유 미기록"`, 빈 문자열로
  남기지 않는다)

러너가 `executor.enter()` **직후 성공·거부 양쪽 다** `record_entry_result()`를 부른다
(`live/zone_limit_runner.py`). 이로써 세 상태가 **구분된다**:

| DB 모양 | 뜻 |
| -- | -- |
| `filled` + `entered` | 정상 — 포지션이 열렸다 |
| `filled` + `rejected` + 사유 | **정상 동작** — 가드가 걸렀고 이유가 장부에 있다 |
| `filled` + `entry_status IS NULL` | **처분 미기록** = 러너가 두 쓰기 사이에서 죽었다 |

📌 **셋째 줄이 이 이슈의 산출물이다** — 두 쓰기(`record_filled` → `record_open`)는
원자적이지 않으므로, 그 사이에서 죽으면 복구할 수 없다. 그것을 **없앨 수는 없지만
보이게는 할 수 있다**: `orphan_fills()`가 그 행만 골라 주고 `fill_report`·`doctor`가
별도 섹션으로 찍는다. **이제 "진짜 유실"에는 고유한 서명이 있다.**

⚠️ **옛 DB의 `filled` 행은 전부 NULL이라 같은 모양으로 잡힌다** — 그건 유실이 아니라
**판별 불가**다. 도입 이후만 보려면 `orphan_fills(since_ms=…)` /
`alphablock doctor --orphans-since YYYY-MM-DD`(KST).

### 2-2. 마이그레이션 — 서버 DB는 옛 스키마다

`CREATE TABLE IF NOT EXISTS`는 **이미 있는 테이블의 열을 늘려 주지 않는다.** 서버
`live_limit_orders`는 WAN-45 시절 스키마이므로 마이그레이션 없이 새 코드를 올리면
러너가 **첫 체결에서 `OperationalError`로 죽는다**(고치려던 것보다 나쁜 사고). `OrderJournal.__init__`이
`PRAGMA table_info`로 열 존재를 보고 `ALTER TABLE ADD COLUMN`을 건다(멱등 · SQLite에서
O(1) · 기존 행은 NULL). 회귀 테스트가 **옛 스키마 DB를 손으로 만들어** 고정한다.

### 2-3. 거부를 조용히 넘기지 않는다

* **텔레그램**: `format_entry_rejected` 신설 — "지정가는 체결됐으나 포지션을 열지
  않았습니다 — {사유}". 스위치는 기존 `filled`를 **함께 쓴다**(새 스위치를 만들면 기본값에서
  꺼진 채널이 하나 더 생겨 같은 침묵이 재발한다).
* **로그**: 거부는 INFO → **WARNING**.
* **`fill_report`**: `진입`·`거부`·`미기록`·`진입%` 열 추가 + 처분 미기록 섹션.

📌 **`진입%`는 체결률과 곱해 읽는 값이다.** 거래가 되는 비율 = 체결률 × 진입%.
"체결률 81%"(WAN-123/124)를 거래 성립률로 오독하지 않으려면 두 값이 같이 보여야 한다.
⚠️ **이것이 옛 체결률 수치를 무효화하지는 않는다** — 백테스트도 같은 가드로 후보를
버리므로 두 축의 비교는 여전히 성립한다. 새로 보이게 된 것은 **그 손실의 크기**다.

### 2-4. `alphablock doctor` (§2·§4·§5의 도구)

`data/integrity.py` + CLI. 읽기 전용이 기본이고 이상이 있으면 **종료 코드 1**(cron·감시에
바로 물릴 수 있다). 보는 것: `PRAGMA quick_check` · 테이블 인구조사(빈 장부 표시) ·
복구 산출물(`lost_and_found`) · 처분 미기록 체결 · 공간·저널·디스크 여유.

📌 **인구조사가 WAN-194의 판별 논리를 자동화한다** — PM이 손으로 세어 "`backtest_*`는
성한데 장부만 0" → "광범위 유실이 아니다"를 알아낸 그 표다.

🚨 **의도적으로 하지 않는 것 둘**: (1) **자동 `VACUUM` 없음** — 3.8GB DB의 VACUUM은 같은
크기의 임시 파일을 만들고 DB를 **독점 락**한다. 수집기·러너가 붙은 서버에서 코드가 스스로
돌 일이 아니라, 회수 가능 크기만 보고하고 명령은 사람이 고른다. (2) **자동 복구 없음** —
`.recover`를 코드가 돌리면 이 이슈가 겪은 "누가 복구했는지 모르는 DB"를 저장소가 스스로
만들게 된다. `--drop-recovery-artifacts`만 파괴적이고 명시적 옵트인이며 앱 테이블은
건드리지 않는다(테스트가 고정).

## 3. LINK 건의 원인을 「확정」하지는 않았다

⚠️ **정직하게 적는다: 이 세션에는 서버(rocky@orderblock) 접근이 없어 그 LINK 행의
`stop_price`를 보지 못했다.** 그러므로 아래 둘 중 어느 쪽인지 **단정하지 않는다**:

* **(a) 손절폭 가드 거부** — 존 하단이 체결가 8.3586714의 0.3%(≈0.0251) 안쪽이면 사이징이
  0을 내고 거부된다. 관측된 모양과 정확히 일치하고, **재현 테스트로 그 인과를 확인했다**
  (`test_rejected_entry_is_recorded_not_silent`: 좁은 존 → 체결 1건 → 포지션 0 → 거래 0).
* **(b) 두 쓰기 사이의 죽음** — 07-24 강제종료 이력(`faulthandler … exit=True`)이 있어
  배제할 수 없다.

📌 **그리고 그것이 이 수정의 요점이다** — 고친 코드는 **어느 쪽이든 스스로 답을 남긴다**.
다음에 같은 일이 나면 (a)는 `rejected` + 사유로, (b)는 `orphan_fills`로 찍힌다.
서버에서 다음 한 줄이 지금 당장 그 행을 분류해 준다(마이그레이션 후):

```bash
uv run alphablock doctor --skip-quick-check
```

## 4. §1 타임라인에 넘기는 실측 (로컬 파일 — 서버 교차 확인 필요)

PM 코멘트는 로컬 마운트 파일을 *"안 돌아가는 낡은 복사본이라 서버 사고의 증거가 아니다"*
로 정리했는데, **실측은 그보다 미묘하다**:

| 파일 | 크기 | mtime | `lost_and_found` | `paper_trades` | `live_runner_sessions` |
| -- | --: | -- | --: | --: | --: |
| `data/ohlcv.db` | 3.5GB | 07-25 11:59 | **2,827,970** | 2 | 8 |
| `data/ohlcv.db.corrupt.bak` | 1.4GB | 07-26 01:09 | **없음** | 2 | 1 |
| `data/ohlcv.db.old` | 1.4GB | 07-26 01:09 | **없음** | 2 | 1 |

📌 **로컬 `ohlcv.db`의 `lost_and_found` 행 수가 PM이 서버에서 읽은 283만(2,827,970)과
글자 그대로 같다.** 7자리 우연은 없으므로 이 파일은 **서버의 복구된 DB와 같은 복구
사건을 공유한다**(스냅샷이거나 동기 사본). 즉 "서버 사고와 무관한 낡은 복사본"이라는
정리는 이 파일에는 **맞지 않을 수 있다**.

📌 **`.corrupt.bak`·`.old`에는 `lost_and_found`가 없다 = 복구 이전 상태다.** 그리고 둘 다
`paper_trades` **2행을 갖고 있다**(서버 현재 0행) — §4의 "매매 기록 복원 가능한가"에
대한 후보 소스다. 다만 세션 수(1 vs 8)·크기(1.4GB vs 3.5GB)가 달라 **현재 DB의 직전
판이 아니라 더 오래된 별개 DB**로 보인다.

⚠️ **이것을 결론으로 쓰지 말 것** — 서버 파일을 못 봤으므로 mtime·행 수의 해석이 바뀔 수
있다. §1이 서버에서 확인할 것: `~/.bash_history`의 `recover`/`.dump`, journald의
`malformed`/`corrupt`, 서버에 남은 백업 유무, 그리고 **로컬 파일이 서버 마운트인지**.

## 5. 안 한 것 (범위 밖 · 서버 대기)

* **§1 손상·복구 타임라인 확정** — 서버 접근 필요.
* **§2 서버 DB 무결성 검증** — `alphablock doctor`로 실행 가능하나 **서버에서 돌려야
  한다**(로컬 3.5GB 실측 12초 — 서버도 그 수준일 것).
* **§4 `lost_and_found` 정리** — 명령은 만들었고 **실행은 사용자 결정**이다(283만 행 삭제 +
  VACUUM은 러너 정지가 선행).
* **§5 근본 원인** — `doctor`가 디스크·WAL·프리리스트를 숫자로 내지만, 07-24 강제종료가
  손상 벡터인지 확정하려면 서버 로그가 필요하다. **재발 방지(무결성 주기 점검·백업 회전)의
  자동화는 배선하지 않았다** — cron 등록은 운영 결정이라 임의로 넣지 않았다(`doctor`의
  종료 코드가 그 배선의 준비다).
* **두 쓰기의 원자화** — 장부(`OrderJournal`)와 페이퍼 저장소(`PaperTradeStore`)가 각자
  커넥션을 들고 있어 한 트랜잭션으로 묶으려면 저장 계층 재설계가 필요하다. 이 이슈는
  **유실을 없애는 대신 보이게** 했다(별도 이슈 후보).
* **기본값·토대 불변** — 손절폭 가드(0.3%)는 **손대지 않았다**(WAN-76/79 소관 · 변경은
  재-베이스라인 = 사용자 결정). 존폭 필터 1.28 · 오프셋 2bp · `intrabar_live` ·
  `unconditional` · 고정 1.5R · 롱 온리 전부 그대로다.
