# WAN-324 — 타임라인 하루치 적재: 프로파일(§0)과 1분봉 1회 읽기(§1)

**결론**: §0 프로파일은 이슈의 가설을 **절반만** 지지한다 — 1분봉을 종목당 4번 읽는 것은
사실이고 그 낭비는 실재하지만(로컬 41.9s → 10.5s), **로컬에서 지배적인 단계는 서브스텝
평가(72%)** 다. 그럼에도 §1을 착수한 근거는 **서버의 `user`/`real` 분해**다(아래 §0-3):
서버가 기다린 4분은 CPU가 아니라 I/O이고, 이 경로에서 I/O를 내는 단계는 1분봉 SQL 하나다.
§1 구현 후 **캐시 48셀 × 100행이 변경 전후 비트 단위로 동일**하고(§1-2) 로컬 하루치 적재의
CPU 시간은 **141.9s → 114.6s(−19%)** 다. **서버 재측정은 사용자 몫으로 남는다**(세션에 SSH 없음).

⚠️ **성능 전용이다** — 엔진·전략·기본값·토대 불변(`ConfluenceParams()`·`LeverageBookParams()`),
DB에 아무것도 쓰지 않으며(프로파일러는 순수 측정), `ALPHABLOCK_LIVE_TRADING=false` 유지.
**숫자가 바뀌면 그건 버그다**(WAN-203이 성능 수정을 비트 동일로 하고 측정과 분리한 방식).

## §0 — 프로파일 (완료 기준 1)

재현: `uv run alphablock timeline-profile --day 2026-07-20 --shape per-cell|shared`
(신설 `live/timeline_profile.py` · 순수 측정 · 종료 코드 항상 0).

**어디서 쟀나**: 로컬 M1(Darwin arm64 · CPU 8) · 2026-08-19 14:49~14:54 KST ·
**직렬(jobs=1)** · 채택 좌표 12종목 × 4TF = 48셀 · 워밍업 120일 · 날짜 2026-07-20.
🚨 **경합 상태**: 같은 머신에서 `backtest.wan330_partial_tp_ladder_4tf --jobs 4`가 도는
중이었다(load average 6.7~8.1). 절대 시간은 그만큼 부풀려져 있으니 **비중과 두 모양의
차이**로 읽을 것 — 이슈가 「측정할 때 그 경합을 기록할 것」이라 요구한 자리다.

**사실로 확인됐다**.

### §0-3 §1 착수 판단 — 게이트를 어떻게 통과했나

이슈는 「§0 결과가 **1분봉 읽기가 지배적이지 않다**로 나오면 §1은 착수하지 않고 닫는다」고
못 박았다. 로컬 수치만 보면 1분봉은 25%라 **지배적이지 않다**. 그런데 로컬은 7.8GB DB를
다른 프로세스가 계속 두드려 **페이지 캐시가 뜨겁고**, 서버는 그 반대다. 서버 실측
(WAN-322, 2026-08-18)의 분해가 그 간극을 가른다:

| | 서버(2026-08-18) | 로컬 이번 측정 |
| --- | ---: | ---: |
| `real` | 6분 23초 (383s) | 2분 54초 (174s) |
| `user` (CPU) | 2분 13초 (**133s**) | 2분 21초 (141s) |
| 차이(≈ I/O 대기) | **≈ 250s** | ≈ 33s |

📌 **서버의 `user` 133초는 로컬 CPU 단계(탐지 2.6s + 평가 120.7s ≈ 123s)와 거의 같다** —
즉 **서버가 느린 이유는 CPU가 아니고**, 남는 250초는 이 경로에서 I/O를 내는 유일한 단계인
**SQL 읽기**다. 로컬에서 그 단계가 25%로 보이는 것은 캐시가 대신 내주고 있기 때문이다.
그래서 「지배적이지 않다」는 **로컬 한정 사실**로 기록하고 §1을 착수했다.

⚠️ **CLAUDE.md의 「1분봉 로딩이 1조합 실행의 ~36%」를 이 경로에 인용하지 말 것** — 그건
3년 격자 값이고 여기는 120일 창이다(이슈가 미리 경고한 자리). 이 표가 이 경로의 정본이다.

## §1 — 종목당 1분봉 1회 로드

### §1-1 무엇이 바뀌었나

* **신설 `harness.load_market_data_by_timeframe(symbol, timeframes, …)`** — 상위TF는 TF마다
  읽되 **1분봉은 가장 넓은 창을 한 번 읽어 TF별로 자른다**. 1분봉 창의 하한이 상위TF 첫
  봉의 `open_time`이라 TF마다 다르다는 점(이슈가 짚은 함정)을 그대로 지킨다.
* **병렬 단위가 셀 → 심볼로 올라갔다**(`_BacktestSymbolTask`) — 같은 심볼의 4개 TF가 한
  프로세스에서 한 번 읽은 1분봉을 나눠 쓴다.
* 🚨 **로더는 지연 산출(제너레이터)이다** — 이게 없으면 이 최적화가 **메모리를 오히려
  악화시킨다**. 120일치 1분봉은 TF마다 사본이라(174,240행) 네 TF를 한꺼번에 들면 워커가
  «공유 원본 + 슬라이스 4개» 다섯 벌을 동시에 이고, 그건 이슈 §1-3이 기대한 방향
  (`BrokenProcessPool` 완화)과 **정반대**다. `iter_market_data_by_timeframe`이 TF를 하나씩
  내주고 적재 경로가 하나씩 소비·폐기하므로 살아 있는 사본은 **«공유 원본 + 지금 TF»
  둘**이다. 넷을 나란히 봐야 하는 곳(프로파일러·테스트)만 `load_market_data_by_timeframe`
  (= `dict(iter_…)`)을 쓴다. ⚠️ **화면 버튼은 직렬 유지**(기존 판단 불변).
* **어느 칸을 어떤 순서로 굽는가는 불변** — `_symbol_tasks`가 심볼·TF 첫 등장 순서를
  보존하고 중복 칸을 한 번만 굽는다. 결과 dict는 **입력 칸 순서**로 되돌린다(행 순서가
  거기서 나온다).

### §1-2 비트 동일 게이트 (완료 기준 2) — 통과

**하루치 캐시를 변경 전 코드와 변경 후 코드로 각각 적재해 대조했다**(2026-07-20 · 12종목 ×
4TF · 별도 스크래치 캐시 DB라 공용 DB 불변):

| | 셀 | 행 | 대조 |
| --- | ---: | ---: | --- |
| 변경 전(`origin/main`) | 48 | 100 | — |
| 변경 후 | 48 | 100 | **행 100개 전 필드 차이 0** · 셀 48개 좌표·행수 차이 0 |

대조 필드: `is_long` · `status` · `reserve_ms` · `limit_price` · `fill_ms` · `fill_price` ·
`stop_price` · `take_profit_price` · `tap_index` · `exit_ms` · `exit_price` · `exit_reason` ·
`pnl_pct` · `pnl_amount` · `zone_start_time` · `zone_confirmed_time` · `is_reentry`.

회귀 테스트가 **동작으로** 고정한다(라벨 아님):

* `test_load_market_data_by_timeframe_matches_per_tf` — 공유 로더 ≡ TF별 `load_market_data`
  (실데이터 · `assert_frame_equal`). **TF마다 1분봉 하한이 실제로 다른지도 함께 단언**한다
  — 안 다르면 이 테스트가 아무것도 안 지킨다.
* `test_load_market_data_by_timeframe_matches_per_tf_with_funding` — 펀딩 창은 TF마다 다르다.
* `test_backtest_setup_by_cell_matches_per_cell_loading` — 하루치 셋업 행이 **예전 모양을
  테스트 안에서 직접 재현한 것**과 동일(옛 코드를 저장소에 남겨 두지 않는다).
* `test_shared_shape_reads_1m_once_per_symbol` — **읽은 횟수**로 잰다(이름만 `shared`이고
  여전히 TF마다 읽으면 걸린다 — WAN-91/95/112/123/159 부류의 조용한 실패 방지).
* `test_symbol_tasks_group_cells_preserving_order` — 칸 순서·중복 제거.

⚠️ **비트 동일은 두 번 확인했다** — 처음(dict 판)과 지연 산출 리팩터 뒤에 각각 하루치를
적재해 같은 100행과 대조했다. 리팩터가 **메모리만** 건드렸다는 것을 행이 증언한다.

### §1-3 재측정 (완료 기준 3) — 로컬만, 서버는 사용자 몫

같은 명령(`alphablock trades --day 2026-07-20 --persist-cache`)을 변경 전후로 돌린 값:

| | `real` | `user`(CPU) | load avg | 셀 | 행 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 변경 전(`origin/main`) | 2분 54초 | 141.9s | 8.1 | 48 | 100 |
| 변경 후(dict 판) | 2분 17초 | 116.2s | 7.3 | 48 | 100 |
| 변경 후(지연 산출·최종) | 2분 38초 | **114.6s** | 9.0 | 48 | 100 |

🚨 **`real`이 아니라 `user`를 볼 것** — 이 머신에서 `wan330` 측정이 `--jobs 4`로 도는 중이라
벽시계가 load average를 따라 출렁인다(7.3~9.0). **CPU 시간은 141.9s → 114.6s(−19.2%)로
안정적**이고, 두 「변경 후」 판이 서로 같은 것이(116.2 ↔ 114.6) 지연 산출 리팩터가 속도를
건드리지 않았다는 뜻이다(그건 메모리 조치다).

🚨 **서버 재측정(6분 23초 대비)은 이 세션에서 할 수 없다** — 저장소 세션에 SSH가 없다
(WAN-195/314와 같은 제약). 배포 후 사용자가 한 줄로 재고 이슈에 적으면 완료 기준 3이 닫힌다:

```bash
time uv run alphablock trades --day $(date -d yesterday +%F) --persist-cache
```

📌 **로컬 −19%는 서버 기대치의 하한으로 읽는 편이 맞다** — 로컬에서 줄인 31초는 대부분
**이미 페이지 캐시에 있던** 읽기였고, 서버에서 줄어드는 것은 실제 디스크 왕복이다.
⚠️ 반대로 **상한으로도 읽지 말 것** — 서버 I/O 250초가 전부 1분봉 읽기라는 보장은 없다
(캐시 쓰기·다른 프로세스와의 경합이 섞여 있다). 그 판정은 서버 프로파일이 낸다:
`uv run alphablock timeline-profile --day <날짜> --shape shared` (필요하면 `per-cell`도).

## §2 — `--jobs` 기본값 재검토: 착수 안 함

이슈가 **선택**으로 둔 항목이고, 판단 근거인 「서버에서 몇이 최적인가」는 서버 실측이
있어야 나온다(위 제약). **화면 버튼 직렬 유지**는 기존 판단 그대로다(크래시 없이 도는 게
우선). 서버 재측정 뒤 별도로 다룰 일이다.

## 범위 밖 · 지키기로 한 것

* ❌ **`--warmup-days`를 줄이지 않았다** — `warmup_days`가 캐시 지문에 들어가 기본값이
  아닌 워밍업으로 적재한 캐시는 화면이 **읽지 않는다**(일을 하고도 버튼이 그대로 뜬다).
  지문 설계는 옳다.
* ❌ **캐시 미스 자체는 줄이지 않았다** — 배포마다 엔진 지문이 바뀌어 무효화되는 것은
  설계대로다(WAN-106/253). 한 번의 재계산을 싸게 만드는 것이 전부이고, 그 미스가 화면을
  비우지 않게 하는 것은 WAN-325 소관이다.
* ❌ **적재 경로만 고쳤다 — 다른 per-cell 로더는 손대지 않았다**: `live.live_vs_backtest`
  (`compare`·`stop-width`) · `live.paper_parity`(`parity`) · `backtest.run` · 측정 모듈들이
  여전히 셀마다 `load_market_data`를 부른다. 같은 최적화가 먹힐 자리이되 **각각 자기 비트
  동일 게이트가 필요하고**(그게 이 작업 비용의 대부분이다) 이슈가 지목한 것은 하루치 적재
  하나다. 필요해지면 `iter_market_data_by_timeframe`을 그대로 쓰면 된다.
* ❌ 엔진·전략·기본값 변경 없음 · DB 스키마 변경 없음 · 실거래 보류 유지.
