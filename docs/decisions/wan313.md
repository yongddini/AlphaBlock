# WAN-313 — 페이퍼 러너 한 바퀴 16분: §0 프로파일 · §1 비트 동일 성능 수정 · §2 「멈춤」 판정 개편

- **이슈**: WAN-313 (Urgent, WAN-310 스핀아웃)
- **증상(서버 실측 2026-08-16)**: 12종목 × 4TF = 48 시리즈에서 한 바퀴 **16분 13초**
  (심볼당 70~85초). 15분봉(가장 짧은 작업 TF) 주기를 구조적으로 못 따라가고, 하트비트가
  한 바퀴에 한 번만 찍혀 「멈춤」 판정(2.5 × 60s = 150s)이 **영구 STALE**이었다.
- **결정**: §1(a) **비트 동일 성능 수정**(전략·토대·페이퍼 손익 불변) + §2 판정 개편.
  폴링 주기·감시 좌표는 손대지 않았다(이슈 범위 밖 금지 준수).

## §0. 어디에 시간이 가는가 — 단계별 프로파일

로컬(M1 · `data/ohlcv.db` 7.3GB · 9종목 × 4TF = 36시리즈, 12종목 데이터는 서버에만 있어
9종목으로 측정)에서 `poll_series`의 실제 단계를 재현해 잰 값. 표는 TF별 평균(초/시리즈).

| 단계 | 15m | 1h | 2h | 4h | 빈도 |
|---|---|---|---|---|---|
| A. `store.load(sym, tf)` 전체 이력 로드 | **0.497** | 0.116 | **5.808** | 0.036 | **매 폴링** |
| B. closed 필터 + tail(1500) | 0.000 | 0.000 | 0.000 | 0.000 | 매 폴링 |
| C. `window_gap_summary` | 0.001 | 0.001 | 0.001 | 0.001 | 새 HTF 봉마다 |
| D. `OrderBlockDetector.run`(1500봉) | 0.006 | 0.006 | 0.006 | 0.005 | 새 HTF 봉마다 |
| E. `atr`(1500봉) | 0.001 | 0.001 | 0.001 | 0.001 | 새 HTF 봉마다 |
| F. 1분봉 증분 로드 | 0.002 | 0.001 | 0.002 | 0.001 | 매 폴링 |

- **매 폴링 로드 비용(36시리즈 합) = 58.2초.** 심볼당 ≈ 6.5초(15m 0.5 + 1h 0.12 +
  **2h 5.8** + 4h 0.03). 서버는 CPU가 이 파이썬 루프에서 ~12배 느려 심볼당 70~85초 —
  **관측된 16분 사이클과 정확히 부합**한다.
- **병목 1 (지배적): 파생 2h 로드.** `2h`는 저장 행이 없어 매 폴링 **1h 전체 6년(52,559행)
  로드 + `resample_ohlcv`의 버킷당 파이썬 루프(26,279 버킷)** 를 돌았다 — 시리즈당 5.8초의
  거의 전부가 리샘플 루프다(로드 자체는 0.11초).
- **병목 2: 전체 이력 로드.** `poll_series`가 매 폴링 `store.load(symbol, timeframe)`를
  **창 제한 없이** 호출했다 — 15m은 21만 행을 읽어 1,500봉만 쓴다. WAN-121이 백테스트에서
  「1조합의 ~36%」로 측정한 그 축의 러너 판이다.
- **WAN-203 수정의 러너 적용 여부(이슈 §0 첫 확인 항목)**: 그 두 수정(밴드 시딩
  O(N×W) · 서브스텝 오프셋)은 토대 계층이라 러너 경로에도 이미 적용돼 있다 — 이번 병목은
  그와 별개의 **로드 계층**이다.
- 엔진 연산(D·E)은 새 HTF 봉이 닫힐 때만 돌아 상시 비용이 아니다(ms 수준).
  `engine_state` 저장(WAN-306)은 서브스텝당 행 1개 교체(ms 수준)로 병목이 아니다.

## §1. 수정 — 둘 다 비트 동일 (WAN-203 선례)

### 수정 1: 창 제한 로드 (`OhlcvStore.tail_window_start` + 러너 배선)

`poll_series`·`restore_state`가 전체 이력 대신 **「마지막 확정봉 lookback(1500)개」를
정확히 덮는 앵커부터** 로드한다. 근사가 아니라 **정확한 앵커**다:

- 네이티브 TF: SQL로 「end 이하 확정봉 중 최근 bars개」의 최소 `open_time`을 seek.
- 파생 2h: 원본(1h) 시각열을 DESC로 훑으며 **완전(구성 봉 빠짐없음) + 확정(전부
  closed)** 버킷을 세어 bars번째 버킷 시작을 앵커로 — 리샘플의 확정봉 정의와 같은 판정.
- 앵커의 상한(end)은 이번 폴링의 **가장 이른 cutoff**에서 유도한다(따라잡기 재생 중에도
  창 내용이 전체 로드와 같도록). 대충 `bars × 주기`를 빼는 방식은 갭이 있는 시리즈에서
  창 내용이 달라져 **갭 검사 결과까지 갈리므로** 쓰지 않았다.

창 구성(`closed` 필터 → `open_time ≤ cutoff` → `tail(1500)`)이 전체 로드와 **글자
그대로 같음**을 실데이터(3심볼 × 4TF × priming/따라잡기/복원 3케이스 × cutoff 다중)로
확인했고, 합성 갭·미확정·결측 짝 케이스는 회귀 테스트가 고정한다.

### 수정 2: `resample_ohlcv` factor=2 벡터화

버킷당 파이썬 루프를 **factor == 2일 때만** 벡터화 경로로 바꿨다. 버킷당 원소가 2개뿐이라
모든 집계(first/last/max/min/**합**/all)가 연산 순서와 무관 = **수학적으로 비트 동일이
보장**된다. factor > 2(1m→15m 등 집계 백필, WAN-175)는 volume 합의 부동소수 누적 순서가
구현마다 달라질 수 있어 **기존 루프를 유지**한다(집계 백필 산출물 불변).

실데이터(BTC/ETH/DOGE 1h 전체 → 2h)에서 옛 루프와 `assert_frame_equal(check_exact=True)`
**비트 일치** 확인. 속도는 5.7~6.0초 → **27~38ms** (~200배).

### 효과 (로컬 실측)

| | 수정 전 | 수정 후 |
|---|---|---|
| 매 폴링 HTF 로드(36시리즈 합) | 58.2s | **0.32s** (~180×) |
| 2h 시리즈당 | 5.8s | ~0.02s |
| 48시리즈 환산 | ~78s | **~0.43s** |

서버(~12배 느림)로 환산해도 한 바퀴 ≈ **수 초** — 폴링 간격(60s) 안이고 15분봉 주기(완료
기준 2) 대비 두 자릿수 여유다. 페이퍼 손익·이벤트·장부는 **비트 동일**(완료 기준 4):
동작 동일성은 `test_bounded_htf_load_matches_full_load_behavior`(앵커 경로 vs 전체 로드
경로의 이벤트·지표 시딩 비교)가 고정한다.

### 택하지 않은 것

- **(b) 시리즈 병렬화** — §0이 지목한 병목이 로드 계층이라 필요 없었다. 레버리지 북
  공유 자본의 배치 순서 결정성(WAN-305 파리티)을 건드릴 이유가 없다.
- **(c) TF별 폴링 주기 분리** — 같은 이유로 불필요. 새 자유 파라미터를 만들지 않았다.

## §2. 「멈춤」 판정 개편

구조 문제: 하트비트가 **한 바퀴 완주에 묶여** 있어 시리즈 수가 늘수록 간격이 길어지는데
판정 문턱(2.5 × 폴링 간격)은 셀 수를 모른다. 좌표를 넓힐 때마다 오경보가 악화됐다.

1. **하트비트를 시리즈 단위로** — `poll_once`가 시리즈 하나를 마칠 때마다
   `RuntimeStateStore.touch`(하트비트만 갱신, 상태 보존). 하트비트 간격이 시리즈 수와
   무관해져 기존 문턱(150s)이 다시 유효하다.
2. **「마지막 완주」를 별도 지표로** — `last_cycle_completed_at` / `last_cycle_duration_ms`
   를 상태 파일에 남긴다. 하트비트만 뛰고 한 바퀴를 못 끝내는 상태가 초록불이 되지 않게.
3. **완주 예산 = 감시 TF 중 최단 주기**(`runner_cycle_budget_ms`, 15m → 900s) — 「한
   바퀴가 최단 TF 주기 안」이라는 완료 기준 그 자체에서 유도했다(새 자유 파라미터 없음).
   판정: 완주 이후 경과 > `max(2.5 × 폴링 간격, 예산)` → STALE. 완주 기록이 아직 없으면
   (기동 직후·따라잡기 재생 중) 하트비트가 살아 있는 한 경보하지 않는다.
4. **경고 문구 분리** — 하트비트 끊김(프로세스 정지 의심)과 완주 지연(살아 있으나 못
   따라감)은 원인 안내가 다르다(텔레그램 `health_watch`·대시보드 Health 탭·상단 pill
   전부 같은 판정 함수 하나를 공유).

최소 요건(정상 초록 · 정지 빨강)은 `tests/test_health.py`·`tests/test_health_watch.py`·
`tests/test_zone_limit_runner.py`가 **동작으로** 고정한다.
