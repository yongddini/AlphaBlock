# WAN-365 — 소급 취소를 인과로: `invalidation_cancel` 기본값을 `bar_close`로

**재-베이스라인(사용자 결정 2026-08-23 「일단 고쳐야지」) · WAN-364 실행 · 엔진 정확성 1층.**
새 격자는 돌리지 않았다 — 근거는 WAN-364가 이미 낸 표다. 재현:

```bash
uv run python -m backtest.run --oos-warm                        # 채택 북(= 인과)
uv run python -m backtest.run --oos-warm --invalidation-cancel bar_open   # WAN-365 이전 북
```

관련: [`wan364.md`](wan364.md)(근거·선행) · [`wan149.md`](wan149.md)·[`wan132.md`](wan132.md)
(같은 급 재-베이스라인의 파급 처리 선례) · [`wan305.md`](wan305.md)(측정은 채택 규칙 위에서).

## 0. 한 줄

**존이 깨지는 봉의 대기 지정가를 봉 시작으로 소급 취소하지 않는다.** 체결시킨 뒤 손절
규칙에 맡긴다. `ConfluenceParams.invalidation_cancel` 기본값이 `"bar_open"` → `"bar_close"`다.

WAN-364의 순서 논증 그대로다 — 롱 지정가는 존 **안**에 있고 손절선은 존 **아랫변**이라
`가격 하락 → 체결 → 계속 하락 → 무효화(손절)` 순서가 **강제된다**. 무효화 시점엔 이미
포지션을 들고 있어 **취소할 주문이 없다**. 사용자 지적: *"손절을 해야지 뭘 취소한다는 거냐"*.

## 1. 알고 받는 것 — 성과가 나빠진다. 그게 맞는 숫자다.

채택 좌표 북(12종목 × 4TF 한 지갑 × 못 박은 6년 · 재진입 ON(band) · cap_only 5배),
출처 [`wan364.md`](wan364.md) §4:

| | 거래 | 승률 | 거래당 net R | MDD |
| -- | --: | --: | --: | --: |
| 전환 전(소급 취소) | 6,336 | 55.33% | **+0.1985** | 22.90% |
| **전환 후(인과)** | **9,514** | **40.28%** | **−0.1798** | **100.00%** |

되살아나는 3,309건은 **손절 2,922 · 익절 387**(거래당 −0.8958R). 사용자가 이 사실을 알고
골랐다.

⚠️ **「그래서 전략이 손실이다」로 확정하지 말 것** — 여전히 `baseline`(닿으면 체결) 위 값이고,
체결 보수화(`pen_5bp`)와 **인과 팔 위의 대조군 실험은 아직 안 쟀다**. 확정된 것은 하나다:
**옛 플러스가 「지워진 손절」 덕이었다.**

🚨 **「청산 0건」이 여기서 아무것도 보증하지 않는다** — 인과 팔은 MDD 100%인데 청산 트리거가
0이다(사이징이 현재 자본의 %라 연쇄 손실로는 조건이 구조적으로 안 걸린다, WAN-312 §4 ·
WAN-367).

## 2. 무엇을 바꿨나 — 축을 **파라미터로 올렸다**

WAN-364는 이 축을 `build_zone_limit_candidates(invalidation_cancel=)` **kwarg**로 만들었다.
그대로 두면 파급 처리가 불가능에 가깝다 — 엔진에 닿는 호출부가 `backtest/` 안에만 ~110곳이고,
그 대부분은 `params`만 넘기고 취소 시점은 기본값에 맡긴다.

그래서 값을 **`ConfluenceParams.invalidation_cancel`로 올렸다**. 이 자리가 맞는 이유:
`limit_valid_bars`(유효기간 만료 취소)·`cancel_limit_on_condition_fail`(조건 미충족 취소)이
이미 **같은 「주문 취소 규약」 가족**으로 그 클래스에 산다.

- kwarg는 **오버라이드로 남는다**(`None` = 파라미터를 읽는다) — `rsi_gate_mode` 오버라이드와
  같은 규약이라 wan364의 두 팔은 그대로 돌고 그 CSV는 비트 재현된다.
- `ADOPTED_INVALIDATION_CANCEL`은 **리터럴을 다시 적지 않고** `ConfluenceParams()`에서 읽는다.
  「채택 기본값」이 두 곳에 살면 언젠가 갈라진다(WAN-91/95/112/123/159가 반복해 겪은 자리).
- 신설 `harness.LEGACY_INVALIDATION_CANCEL`(= `"bar_open"`) · `harness.pin_invalidation_cancel`
  — `pin_band_bar`(WAN-132)·`pin_zone_width`(WAN-159)와 **같은 자리·같은 관행**.
- `harness.build_params(invalidation_cancel=…)`는 `offset_bps` 규약이다(`None` = 손대지 않는다).

📌 **부수 효과 하나가 실제로 좋아졌다** — 취소 시점이 `params`를 타므로 `run_cells`의
**표준 경로 검산**(`engine_check` → `harness.run_once`)이 **두 팔 모두에서** 성립한다. 옛
배선에서는 인과 팔의 검산을 끌 수밖에 없었다.

## 3. CLI — 미지정과 `bar_open`을 가른다

`--invalidation-cancel {bar_close,bar_open}`:

| 준 값 | per-cell | 북 |
| -- | -- | -- |
| **미지정** | 채택(인과) | 채택 북(인과) |
| `bar_close` | 인과(명시) | 인과(명시) |
| `bar_open` | **WAN-365 이전 동작** | **WAN-365 이전 채택 북**(옛 CSV 재현) |
| `bar_close,bar_open` | 격자 2팔 | **거부**(exit 2) |

WAN-159(`none` vs 미지정)·WAN-273(`off` vs 미지정)과 **같은 규약**이다 — 안 가르면 「옛 동작」
라벨을 단 채 조용히 인과로 도는 실패가 된다. 북이 격자를 거부하는 이유는 WAN-316과 같다:
**한 실행이 한 지갑**이라 두 취소 시점을 한 표에 넣을 수 없다.

## 4. 파급 — 이 이슈의 실제 작업량

🚨 `invalidation_cancel`은 **WAN-364가 처음 만든 축이라 기존 리포트가 하나도 명시하지
않았다**. 고정하지 않으면 옛 결론 리포트 전부가 조용히 인과 엔진으로 다시 돌아 본문과
어긋난다 — WAN-149(`combine_obs`)·WAN-132(`band_bar`)와 **글자 그대로 같은 함정**이고,
「바꿨다고 믿으면서 안 바뀐 것」의 거울상인 **「안 바꿨다고 믿으면서 바뀐 것」**이다.

**엔진에 닿는 `backtest/wan*.py` 72개 중 70개를 명시 고정**했다.

🚨 **고정 대상을 손으로 적었으면 넷을 빠뜨렸다.** 호출부가 부르는 이름이 `build_zone_limit_
candidates`에서 몇 단계 떨어져 있는 자리가 있다 — `wan142.build_cell`(wan154·wan176·wan203이
빌려 쓴다) · `wan70.run_random_control_b_evals`(wan350). 그래서 고정 목록을 **전이 폐포**로
구했고(아래 §4-3), 그 넷은 **모듈 자신의 파라미터 빌더**에서 고정했다.

### 4-3. 회귀 테스트가 라벨이 아니라 **동작**으로 고정한다

`tests/test_wan365_invalidation_rebaseline.py`:

- 채택 기본값이 인과이고 **한 곳에서만 산다**(`ADOPTED_INVALIDATION_CANCEL is
  ConfluenceParams().invalidation_cancel`).
- **다른 채택 기본값은 하나도 안 움직였다**(존폭 1.28 · 1.5R · 2bp · 24봉 · `intrabar_live` ·
  `unconditional` · 롱 온리).
- **핀이 실데이터에서 후보를 실제로 지운다** — 라벨만 검사하면 파라미터가 엔진에 안 닿아도
  통과하므로, 「되살아난 거래(`entry_after_invalidation`)가 0건인가」로 건다.
- CLI가 **미지정 ≠ `bar_open`**을 가르고, 북이 격자를 거부하며 단일값은 받는다.
- 🚨 **파급 처리 누락을 코드가 잡는다** — 테스트가 `backtest/*.py`에서
  `build_zone_limit_candidates`에 닿는 함수의 **전이 폐포**를 매번 다시 구하고, 그 함수에
  파라미터를 넘기면서 이 축을 **언급조차 하지 않는** `wan*.py`가 있으면 실패한다. 예외는
  `_UNPINNED_BY_DESIGN`에 **이유와 함께 선언**해야 한다. 목록을 손으로 적으면 `build_cell`
  부류가 빠지므로(위 🚨) 폐포로 구하는 것이 요점이다. 돌연변이 확인 완료 — wan203의 핀을
  빼면 실제로 실패한다.
  ⚠️ **고정 「지점」까지 강제하지는 않는다**(호출부 감싸기 · 빌더 인자 둘 다 정당하다) —
  잡는 것은 **한 모듈이 이 축을 아예 언급하지 않는 것**이다.

`tests/test_wan364_invalidation_cancel.py`는 **그대로 유효**하고, 「어느 쪽이 기본값인가」만
갱신했다(옛 팔은 이제 `invalidation_cancel="bar_open"` 명시). 축이 두 층(시그널·시뮬레이터)을
함께 움직인다는 그 파일의 다섯 가지 고정은 손대지 않았다.

## 5. 얼어붙는 것 (기록)

지우지 않고 **시점 표시**를 단다. 아래 표들은 전부 「그때는 그랬다」다:

- **엣지 판정 계열** WAN-84/88/111/114/124/151/201/248/350 — ⚠️ **방향은 안 뒤집힌다**(결함이
  실제 팔·무작위 팔 **양쪽에 대칭으로** 걸린다). 얼어붙는 것은 **절대 수준**이다.
- **채택 성과 계열** WAN-312/316/323/330/336/346/359 — 특히 **WAN-346의 「거래당 실력
  0.109R ~ 0.199R 사이」라는 폭 판정이 통째로 무효**다(두 끝값이 다 소급 취소 위의 값).
- **파라미터 채택 근거** WAN-159(존폭 1.28) · WAN-197(가드) · WAN-90/143/206(익절 R) ·
  WAN-112(오프셋) · WAN-182/252/307(좌표) · WAN-213(배수) · WAN-273(재진입) — **고른 값 자체는
  안 건드리지만 고른 근거가 된 표가 얼어붙는다.**

그래서 다음 단계가 필요하다.

## 6. 다음 단계 (별건 · 순서가 중요하다)

사용자 결정 *「이제 다시 해봐야지,,, 힘들겠지만」*의 실행. **격자를 통째로 다시 돌리는 것은
불가능하다**(북 한 팔 66~92분 · 축이 일곱이면 조합이 수천).

1. **부품 분해부터**(WAN-366) — 인과 엔진 위에서 사다리(존 단독 → +볼린저 → +존폭 필터 →
   +가드)를 다시 세워 **어느 부품이 아직도 값을 더하는지** 본다. 여기서 아무 부품도 플러스가
   아니면 그 뒤의 스윕은 의미가 없다.
2. 1에서 **살아남은 축만** 스윕한다.
3. **판정은 채택 북에서**(WAN-341). per-cell은 탐색·귀속 진단용.

🚨 **가장 큰 위험은 계산 시간이 아니라 과최적화다.** 기댓값이 음수인 엔진 위에서 축 일곱 개를
뒤지면 **앞구간에서 좋아 보이는 조합은 반드시 나온다.** WAN-161은 배수 argmax가 8셀 중 7에서
IS→OOS로 뒤집히는 것을, WAN-90은 IS 최적이 OOS에서 무너지는 것을, WAN-111은 「어느 심볼이
좋은가」가 구간을 못 넘는 것을 봤다. **OOS는 선택 축이 아니다.**
