# WAN-370 — 수수료 분해(§1) ＋ 익절을 지정가(메이커 2bp)로(§2)

**측정 ＋ 재-베이스라인(사용자 지시 2026-08-25).** 주 산출물은 **§1 비용 분해**이고, §2는 그
분해가 지목한 자리(익절 비용)를 **정확성 근거로** 바로잡는 전환이다. 둘이 한 이슈인 이유는
같은 실행에서 나오기 때문이다 — 분해에 필요한 거래별 내역이 채택 북 한 번을 돌려야 나오고,
전환 재산출이 어차피 그걸 돈다(나누면 같은 격자를 두 번 돈다).

사용자 결정 둘: **① 익절 체결 판정은 안 건드린다**(수수료만) · **② 재산출은 채택 성과 ＋
부품 사다리까지**.

재현:

```bash
uv run python -m backtest.wan370_cost_decomposition --jobs 4   # §1 두 팔(전·후)
uv run python -m backtest.wan370_cost_decomposition --from-csv # 요약만
uv run python -m backtest.wan366_causal_ablation --jobs 4 --skip-census  # 사다리 재산출
uv run python -m backtest.run --oos-warm                       # 채택 성과(= 새 회계)
```

관련: [`wan235.md`](wan235.md) §3-2·§3-4(익절 지정가 집행을 정해 놓고 백테 비용은 미뤄 둔
자리 — **그 미뤄 둔 결정이 이 이슈다**) · [`wan95`](../..) 진입 쪽 같은 전환 ·
[`wan132.md`](wan132.md)(정확성 근거 전환의 패턴) · [`wan366.md`](wan366.md)/[`wan368.md`](wan368.md)
(재산출 대상 사다리) · [`wan341.md`](wan341.md)(판단은 북에서만) · [`wan305.md`](wan305.md).

## 0. 한 줄

**익절(부분 익절 포함) 청산이 메이커 2bp·슬리피지 0으로 값매김된다.** 손절·만료·데이터
종료는 테이커 4bp＋5bp **그대로**다. `BacktestConfig.take_profit_liquidity` 기본값이
`taker` → **`maker`**.

🚨 **근거는 정확성이지 수익이 아니다.** 실거래 집행은 이미 「손절 = 시장가 reduce-only ·
**익절 = 지정가 reduce-only**」로 정해져 있었다(`wan235.md` §3-2). 백테스트 비용만 그걸
따라가지 않았다 — WAN-95가 **진입** 쪽에서 한 교정("실매매가 지정가면 계산도 지정가")의
익절 판이고, 아무도 물은 적이 없어 지금까지 굴러왔다.

⚠️ **체결 판정은 안 바뀐다**(사용자 결정 ①) — 「닿으면 체결」 그대로다. 그래서 **수수료는
지정가인데 체결은 낙관**인 상태가 되고, 그 사실을 여기 명시한다. 익절 축 체결 보수화는
별도 이슈다(진입 쪽이 정확히 그 구조 — `pen_5bp` 민감도 렌즈, WAN-104/128).

## 1. §1 — 비용 분해 (주 산출물)

### 1-0. 무엇을 쟀나

인과 엔진의 채택 북은 거래당 net R이 **−0.1798R**인데(WAN-366 `L4` `oos_warm`) 그 숫자는
**이미 수수료를 뺀 뒤**라, 안에 두 가지가 뭉쳐 있었다:

* **(가)** 시장에서 제대로 졌다 — 가격이 반대로 갔다
* **(나)** 시장에선 거의 비겼는데 **수수료가 다 먹었다**

같은 −0.1798R인데 다음에 할 일이 완전히 다르다. 이 표가 그 한 덩어리를 **gross / 진입
수수료 / 익절 수수료 / 손절 수수료 / 슬리피지 / 펀딩**으로 쪼갠다.

📌 **새로 잰 것은 없다** — `common.costs.CostBreakdown`(WAN-37)의 산식을 북 거래 하나하나에
적용해 R 단위로 평균낼 뿐이다. **이미 잰 것을 갈라 본다.**

자는 **거래당 net R**이다(총수익 %는 6년 복리라 판정 자가 아니고, 이 좌표에서는 아예
−100%로 포화한다 — WAN-169/213). ±0.005R 안은 「0과 구분되지 않는다」로 읽는다(WAN-366 규약).

### 1-1. 판정 — **(나) 시장에선 벌었는데 비용이 다 먹었다**

채택 북(12종목 × 4TF 한 지갑 × 못 박은 6년 · 인과 · 재진입 ON · cap_only 5배), 주 구간
`oos_warm` 9,514거래(전 팔 기준):

| | 전(익절 테이커) | 후(익절 메이커, **채택**) |
| -- | --: | --: |
| **시장에서 얻은 것 (gross)** | **+0.0918R** | +0.0920R |
| − 슬리피지 | 0.1698 | 0.1350 |
| − 진입 수수료 | 0.0340 | 0.0340 |
| − **익절 수수료** | 0.0278 | **0.0139** |
| − 손절 수수료 | 0.0401 | 0.0401 |
| − 펀딩 | −0.0002 | −0.0002 |
| **= 총비용** | **0.2716** | **0.2229** |
| **= 최종 net R** | **−0.1798** | **−0.1309** |

* **gross +0.0918R은 노이즈선(±0.005R)의 18배** — 시장에서는 이기고 있었다. 비용(0.2716R)이
  그 3배라 최종이 마이너스다. **비용이 net R 손실의 151%를 설명한다**(전 팔 기준).
* **전환의 몫 = +0.0489R**(−0.1798 → −0.1309). 🚨 **부호는 안 바뀐다** — 비용을 전부 0으로
  만들어도 천장이 +0.09R이다. 「비용만 고치면 흑자」가 아니다.
* 🚨 **최대 비용은 익절 수수료가 아니라 슬리피지다(총비용의 62%)** — 그중 익절 청산의
  5bp가 전환으로 함께 사라져, 절감이 「익절 수수료 절반」(0.014R)이 아니라 총 0.049R이다.
* ⚠️ 두 팔의 거래 수가 4건 다르다(30,251 vs 30,255) — 후보는 같아도(검산 (d) = 0) 공유
  자본이라 손익이 뒤쪽 사이징을 움직인다(WAN-312 성질 · 문서화된 그대로).

## 4. 사다리(WAN-366) 재산출은 하지 않았다 — 산수로 닫힌다 (사용자 결정 2026-08-25)

완료기준의 「부품 사다리 재산출」은 **§1 실측에 기반한 논증으로 대체**됐다(사용자 결정:
*"굳이 사다리를 다 돌려야 해? 하나로만 봐도 비용이 얼마나 차지하는지는 알지 않나"*).
`wan366_causal_ablation.csv`는 **옛 회계 위의 기록으로 시점 배너를 달고 보존**된다(재산출
비용 6~10시간 회피). 논증:

**전환이 사다리 순위를 바꾸려면 「팔 간 절감의 차이」가 그 단의 증분보다 커야 한다.**
절감의 전체 스펙트럼이 §1-3의 버킷 축으로 **+0.012R ~ +0.082R**이므로, 어떤 두 팔의 절감
차이도 **0.070R을 넘을 수 없다**(한 팔이 전부 최협 버킷, 다른 팔이 전부 최광 버킷이라는
극단 가정에서조차). 단별로:

| 단 | 증분(`oos_warm`) | 상한 0.070R 대비 | 판정 |
| -- | --: | -- | -- |
| 가드 `L2→L3` | **+0.2615R** | 3.7배 | **부호 불변** |
| 볼린저 `L0→L1` | **−0.1204R** | 1.7배 · 두 팔 다 필터 꺼짐(같은 분포) | **부호 불변** |
| 존폭 필터 `L1→L2` | **−0.0696R** | 극단 가정으로도 1.0배 · 현실적 이동 ~0.02R | **부호 유지 · 크기 축소 가능** |
| 재진입 `L3→L4` | −0.0145R | 같은 필터·같은 가드 = **같은 손절폭 분포** · 승률 차 0.6%p → 이동 ~0.001R | **부호 불변** |

* 재진입 단이 가장 얇지만 가장 안전하다 — `L3`·`L4`는 손절폭 분포가 같아 절감이 양쪽에
  똑같이 붙는다(절감 차 ≈ 승률 차 × 익절 절감 ≈ 0.001R ≪ 0.0145R).
* 존폭 필터 단만 크기가 실질적으로 줄 수 있다(필터가 손절폭 분포를 가르는 유일한 단) —
  **부호(마이너스 기여)는 유지**되므로 WAN-369의 결정 입력은 방향이 안 바뀐다. 크기가
  결정을 가른다고 판단되면 그때 `L1`·`L2` **두 단만**(후보 생성 1회) 새 회계로 재면 된다.
* 🚨 이 논증은 **증분(팔 간 차)**에 대한 것이다 — 사다리의 **절대 수치**는 전부 옛 회계라
  새 회계 절대값이 필요하면 wan370 CSV(= `L4`의 새 판)를 쓸 것.

## 2. §2 — 엔진: 청산 유동성을 사유별로 가른다

| 청산 사유 | 전 | 후(채택) |
| -- | -- | -- |
| **익절** | 테이커 4bp ＋ 슬리피지 5bp | **메이커 2bp · 슬리피지 0** |
| **부분 익절**(래더, WAN-323) | 테이커 | **메이커** |
| 손절 | 테이커 4bp ＋ 5bp | **불변** |
| 만료·데이터 종료 | 테이커 | **불변** |
| 진입(존 지정가) | 메이커 2bp · 슬리피지 0 | **불변** |

🚨 **요율 값 자체는 하나도 안 바뀌었다**(4bp / 2bp / 5bp) — **붙는 자리**만 바뀐다.

### 2-1. 분기는 한 곳에만 있다

`BacktestConfig.exit_liquidity(reason)`가 **단일 소스**다. 호출부(`_to_trade`의 부분 청산
루프와 최종 청산)가 사유를 안 보고 `Liquidity.TAKER`를 그대로 넘기면, 라벨만 바뀌고 실제로는
전부 테이커로 도는 — 이 저장소가 반복해 겪은 조용한 실패가 된다(WAN-91/95/112/123/159).
리포트(`wan370_cost_decomposition.decompose_trade`)도 그 분기를 **복제하지 않고 물어본다**
(복제하면 엔진과 리포트가 서로 다른 비용을 말한다 — WAN-77의 사본이 실제로 그렇게 갈라졌다).

회귀 테스트는 **라벨이 아니라 동작으로** 건다(`tests/test_wan370_cost_decomposition.py`):
같은 엔진에서 **익절로 끝난 거래와 손절로 끝난 거래의 실제 수수료율이 다른가** ·
익절 체결가에 **슬리피지가 안 붙는가** · 부분 익절도 메이커인가 · 만료는 테이커로 남는가 ·
옛 핀이 옛 손익을 그대로 내는가.

### 2-2. 옛 동작 명시 핀 — 무엇을 어떻게 고정했나

`take_profit_liquidity`는 **WAN-370이 처음 만든 축이라 기존 리포트가 하나도 명시하지
않았다** — `LEGACY_BAND_BAR`(WAN-132)·`LEGACY_COMBINE_OBS`(WAN-149)·
`LEGACY_INVALIDATION_CANCEL`(WAN-365)과 **글자 그대로 같은 함정**이다. 고정하지 않으면 옛
결론 리포트가 전부 조용히 새 회계로 다시 돌아 본문과 어긋난다(「안 바꿨다고 믿으면서 바뀐 것」).

핀은 **두 층에 나눠** 걸었고, 층마다 방식이 다르다:

| 층 | 어떻게 | 기본값 | 채택 옵트인 |
| -- | -- | -- | -- |
| **per-cell** (`harness.build_config`) | 옛 리포트가 `legacy_build_config`을 부른다(**호출 이름**이 곧 핀) | `build_config`은 **채택**(WAN-305) | 인자를 안 주면 채택 |
| **북** (`wan169.run_cells` · `book_cli.iter_book_segments`/`build_book_rows`) | 파라미터 기본값이 **옛 값**(중앙 핀) | **옛 값**(`taker`) | `book_cli.run_book`·wan366·wan370이 **명시로** 넘긴다 |

* per-cell 층은 **호출 사이트가 82곳**이라 「이 표는 옛 회계의 기록」이 호출부에서 읽히게
  이름으로 갈랐다(`pin_band_bar`·`pin_invalidation_cancel`과 같은 자리).
* 북 층은 `wan169.run_cells`/`book_cli`를 **20개 가까운 측정 모듈이 공유**하므로 한 곳의
  기본값으로 그것들을 통째로 보존한다 — `LEGACY_MAX_NOTIONAL_ADV_FRACTION`(WAN-244/279)이
  같은 이유로 이미 그렇게 중앙화돼 있고, 이 축을 그 옆에 나란히 뒀다.
  🚨 **그래서 새 북 측정 모듈은 `harness.ADOPTED_TAKE_PROFIT_LIQUIDITY`를 명시해야 한다** —
  잊으면 옛 회계로 돈다(WAN-305 위반 위험이 남는 자리이고, 그 사실을 여기 기록한다).
* CLI에는 **플래그를 열지 않았다** — `rsi_gate_mode`·`band_bar`와 같은 **핀**이라
  `Grid.take_profit_liquidity`로만 요청한다(동결 CSV와 대조하는 회귀 테스트 전용).
* `legacy_build_config`은 **축을 인자로 받지 않는다** — 받으면 "legacy"라는 이름을 달고 채택
  회계로 도는 호출이 생긴다(테스트가 `TypeError`로 고정).

### 2-3. 파급 — 무엇을 핀으로 고정했고 무엇을 재산출했나

**핀으로 고정(재산출 안 함)** — 옛 수치를 결론 문장에 박아 둔 리포트:

**재산출(새 회계로 다시 돌림)**:
