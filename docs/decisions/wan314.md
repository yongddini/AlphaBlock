## §1. 원인 — 코드로 확정되는 메커니즘

### 1-a. 구조: 스트림은 「접속 이후에 닫힌 봉」만 준다

`run_collector`(`data/collector.py`)의 기동 순서는 엄격히 직렬이다:

```
backfill_all(전 유니버스 꼬리) → repair_on_start(내부 갭) → 펀딩 백필 → 웹소켓 접속
```

- 웹소켓(`data/stream.py`)은 kline **확정 이벤트**(`k.x == true`)만 저장한다 — 접속
  이전에 닫힌 봉은 어떤 경로로도 다시 오지 않는다.
- `backfill_all`은 각 시리즈의 꼬리를 **자기 차례의 시각까지** 채운다. 기존 9종목은
  기동 초에 처리되므로 꼬리 시각 ≈ 기동 시각이다.
- 그 다음 신규 3종목(ADA·DOT·BCH)의 **상장 이후 전체 초기 백필**이 돌면서 접속이
  수십 분 늦어진다(WAN-310 실측: 하트비트 11분 지연 · 기존 종목 1m/5m이 22:53에서 멈춤).
- 그 창(기동 ≈ 22:53 → 접속 > 23:15) 안에 **확정**된 봉은:
  - 백필이 못 채운다(그 심볼 차례엔 아직 안 닫혔다),
  - 기동 갭 복구가 못 본다(그 시점엔 꼬리라 내부 갭이 아니다 — §2),
  - 스트림이 안 준다(접속 전에 닫혔다),
  - **이후 아무것도 다시 요청하지 않는다**(가동 중 갭 복구 없음) → 영구 구멍.

15m 23:00 봉의 확정 시각은 23:15 KST — 접속이 그보다 늦었으므로 정확히 이 봉 하나가
빠진다(22:45 봉은 확정 23:00 이전에… 아래 1-b). 같은 창의 1m 봉들도 같은 이유로 빠져
있어야 하며, 서버 대조는 `scripts/wan314-server-forensics.sh` §2가 확인한다.

### 1-b. 부수 발견 — REST 백필이 형성 중 봉을 「확정」으로 저장하고 있었다

`backfill_symbol`의 필터는 `open_time < end`(end=now)뿐이라 **아직 닫히지 않은 현재
봉**도 통과했고, `candle_from_ccxt`는 기본 `closed=True`로 저장한다. 스트림이 살아
있으면 확정 이벤트가 덮어써 자가 치유되지만, **확정 순간 스트림이 죽어 있으면 부분
봉이 확정 라벨을 달고 영구히 남는다.** 사고에서 22:45 봉(확정 23:00, 기동 백필 시각
22:53에 형성 중)이 정확히 이 조건이다 — 구멍(23:00)은 러너가 거부해서 보이지만,
**부분 봉(22:45)은 어떤 점검에도 안 보인다**(값만 조용히 틀리다). 서버 DB의 그 봉
고가·저가·종가가 22:5x 시점 값으로 잘려 있는지는 포렌식 스크립트 §1이 확인한다.

### 1-c. 인과 판정 (a) 확인됨 — 단, 「굶김」의 정확한 모양

이슈가 물은 「같은 이벤트 루프·같은 SQLite 커넥션·레이트리밋 공유」는 어느 것도
직접 원인이 아니다(백필은 `to_thread`로 오프로딩되고, 저장소는 락 직렬화를 이미
지원한다). 실제 모양은 더 단순하다: **스트림 접속 자체가 전 유니버스 백필 완료
뒤로 직렬화**돼 있어, 백필이 길어지는 만큼 전 종목의 미수신 창이 늘어난다. 신규
심볼 합류는 그 창을 초 단위에서 수십 분으로 늘린 증폭기다 — **다음 유니버스 확장
때 그대로 재발**하는 구조였다.

### 1-d. 격리(재발 방지) — 이번 PR로 구현

1. **접속 직후 꼬리 따라잡기**(`data/collector.py: TailCatchup` + `stream_klines
   (on_connect=...)`): 웹소켓 접속이 성립한 **직후** 꼬리 백필을 백그라운드로 한 번
   더 돌린다. 접속 후에 돌므로 「접속 이후 확정 = 스트림」 + 「호출 이전 확정 =
   따라잡기」의 합집합이 전 구간을 덮는다 — 기동 창뿐 아니라 **재접속 공백**(스트림
   끊김 중 닫힌 봉 — 같은 부류의 구멍)도 매 접속마다 치유된다. 저장소는 이미 백필
   스레드 + 스트림 루프 동시 접근을 락으로 직렬화하므로 안전하고, 밀린 봉이 없으면
   시리즈당 요청 1건으로 끝난다.
2. **형성 중 봉 저장 금지**(`data/backfill.py`): `open_time + tf <= now`인 닫힌 봉만
   저장한다. 1-b의 부분 봉 사고를 원천 차단하고, 따라잡기가 마지막 봉을 정확한 확정
   값으로 다시 받게 한다(형성 중 봉을 저장하면 꼬리 재개 커서가 그 봉을 건너뛴다).

두 수정은 서로를 보완한다 — ①만 있으면 부분 봉이 커서를 오염시키고, ②만 있으면
창 자체가 남는다. 더 근본적인 격리(스트림 선접속 후 백필 병행, 또는 백필 전용
프로세스 분리)는 기동 순서 전체의 재설계라 **별도 이슈 후보**로만 남긴다 — 위 두
수정으로 관측된 사고 벡터는 닫힌다.

## §2. 갭 복구 판정 — 결함 아님 (재현으로 고정)

`find_gaps`(`data/gaps.py`)는 설계상 **저장된 두 봉 사이**만 갭으로 세고, 마지막 봉
이후(꼬리)는 재시작 백필 소관으로 명시 제외한다(모듈 독스트링 「경계 처리」). 23:25
실행 시점에 저장된 마지막 15m 봉은 22:45였으므로 23:00은 꼬리였고, 「갭 없음(7일
창)」은 **정확한 보고**다.

꼬리가 지나간 뒤(스트림 재개로 23:15 봉이 저장된 뒤)에는 23:00이 내부 구멍이 되고,
갭 복구가 정확히 그 한 봉을 찾아 메운다 — 사고의 실제 타임스탬프로 재현하는 회귀
테스트 2본이 이 동작을 고정한다(`tests/test_repair.py::test_wan314_*`). 수정할 결함이
없으므로 갭 복구 코드는 건드리지 않았다.

⚠️ 단 「다음 복구가 잡는다」의 다음 복구는 수정 전에는 **다음 재시작**(repair_on_start)
또는 수동 `alphablock backfill --repair`뿐이었다 — 가동 중에 생긴 구멍이 오래 사는
이유였고, §1-d의 접속 직후 따라잡기가 그 창 자체를 없앤다.

## §3. 건너뛴 평가의 관측성

- 러너가 결측으로 평가를 건너뛸 때(`_feed_htf_window`) ERROR 로그에 더해
  **`live_runtime_state.data_gap_skips`에 기록**한다(`DataGapSkip`: 시리즈 · 결측 구간 ·
  첫/마지막 관측 · 건너뛴 횟수). 구멍이 메워져 평가가 재개되면 기록을 지우지 않고
  `resolved_ms`로 **해소 표시**한다 — 나중에 성적을 읽을 때 그 구간의 빈칸이 「기회
  없음」이 아니라 「데이터 결측」이었음이 남는다.
- 기록은 상태 파일에서 이어받아 **러너 재시작을 넘어 보존**된다(이어받지 않으면 새
  러너의 첫 record가 빈 목록으로 교체해 침묵이 재발한다 — 테스트가 동작으로 고정).
- Health 탭에 「데이터 결측으로 건너뛴 평가」 카드가 생겼다(진행 중이면 빨간 경고 +
  `alphablock backfill --repair` 안내).
- 건너뛰는 동작 자체는 **바꾸지 않았다** — 없는 봉으로 볼린저·RSI를 계산하면 조용히
  틀린 지정가가 나온다(WAN-156 §3). 고친 것은 구멍이 생기는 것(§1-d)과 안 보이는
  것(§3)이다.

## 서버 몫 (이 세션은 SSH 없음 — WAN-195와 같은 제약)

`scripts/wan314-server-forensics.sh`(읽기 전용)가 서버에서 한 줄로 수집한다:
결측 봉·이웃 봉의 현재 상태(§1-b 부분 봉 검증 포함) · 같은 창의 1m 결측(메커니즘
교차 검증) · collector.log 타임라인(백필/복구/접속 선후) · 상태 파일. 구멍이 남아
있으면 `uv run alphablock backfill --repair`(사용자 수행)로 메운다.
