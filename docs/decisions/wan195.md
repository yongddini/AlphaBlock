# WAN-195 — 손상 타임라인은 07-26이 아니라 **07-22**였고, 「283만 행 쓰레기」의 절반은 유일본 캔들이었다

**날짜**: 2026-07-26 · **상태**: §1 닫음(로컬 증거로 확정) · §4 닫음(판정 + 복원 도구) ·
§2·§5는 **서버 실행 대기**(이 세션에도 SSH 접근이 없다 — 실행 스크립트를 대신 넘긴다) ·
**기본값·토대 불변** · **실거래 보류 유지**(`ALPHABLOCK_LIVE_TRADING=false`)

## 0. 요약 — 이슈의 전제 두 개가 틀렸다

WAN-195는 "서버에 붙어서 돌려 보는 일"로 스핀아웃됐지만, **로컬에 남아 있던 증거만으로
§1과 §4가 닫혔다**. 그리고 둘 다 이슈가 적어 둔 전제를 뒤집는다.

| | 이슈의 전제 | 실측 |
| -- | -- | -- |
| §1 손상 시각 | 로컬 `.corrupt.bak`(07-26 **01:09**)가 사고 시각의 단서 | 🚨 **07-22 22:33~22:38**. 01:09는 **증거를 복사한 시각**이고 그 파일의 *내용*은 3.5일 더 오래됐다 |
| §4 `lost_and_found` | 283만 **고아 행** = 버릴 쓰레기 | 🚨 절반이 **살아 있는 테이블에 없는 5m 캔들 145만 행**이다. 그냥 드롭하면 유일본이 사라진다 |
| §1 "로컬 `data/`가 서버 마운트인가" | 미확인 | **지금은 아니다**(로컬 디스크). 단 **01:09에 FUSE 마운트가 걸려 있었다** — 이것이 §5 최유력 손상 벡터다 |

⚠️ **매매 장부(`paper_trades`·`open_positions`)는 `lost_and_found`에서 복원할 수 없다** —
"찾아봤는데 없다"가 아니라 **담길 수 없다**(§4-2). 그 복원의 유일한 소스는 로컬 스냅샷이다.

## 1. §1 손상·복구 타임라인 — 파일 생성 시각이 갈랐다

로컬 `data/`에 남은 세 DB와 23개 `.fuse_hidden*`을 **읽기 전용**(`mode=ro&immutable=1`)으로만
열어 봤다. 결정적인 자료는 mtime이 아니라 **birth time + SQLite 헤더의 change counter**다.

| 파일 | 크기 | birth | mtime | change counter | `lost_and_found` | 최신 봉 |
| -- | --: | -- | -- | --: | --: | -- |
| `ohlcv.db` | 3.8GB | **07-22 22:38:48** | 07-25 11:59 | **101** | 2,827,970 | 07-22 23:23 |
| `ohlcv.db.corrupt.bak` | 1.4GB | 07-26 01:09:01 | 07-26 01:09:05 | **16,519** | 없음 | 07-22 22:33 |
| `ohlcv.db.old` | 1.4GB | 07-26 01:09:05 | 07-26 01:09:09 | 16,519 | 없음 | 07-22 22:33 |

📌 **change counter가 결론을 준다.** SQLite는 쓰기 트랜잭션마다 이 값을 올린다.
`corrupt.bak`의 **16,519**는 오래 살아 있던 DB이고, `ohlcv.db`의 **101**은 **새로 만들어진
파일**이다 — `.recover`의 산출물이 바로 그 모양이다(빈 파일에 덤프를 부어 만든다).
그 새 파일이 `lost_and_found`를 **가지고 태어났다**.

📌 **그래서 복구 시각 = `ohlcv.db`의 birth = 2026-07-22 22:38:48 KST**다. 앞뒤가 정확히 맞는다:

* 손상 직전 DB(`corrupt.bak`)의 마지막 1분봉이 **22:33**, 마지막 러너 세션 last_seen이 **22:26**
* 복구본 `ohlcv.db` 생성 **22:38:48** (공백 ≈ 5분 = 복구 작업 창)
* 복구본의 다음 러너 세션 시작 **22:47** — 즉 22:26에 끊기고 22:47에 되살아났다

🚨 **`corrupt.bak`·`.old`는 「사고 시각의 단서」가 아니다.** 둘은 **byte-for-byte 동일**하고
(`cmp` 차이 0) 4초 간격으로 연달아 태어났다 = 07-26 01:09에 **같은 원본을 두 번 복사**한
것이다(1.4GB / 4초 ≈ 350MB/s = 로컬 디스크 복사 속도). 내용은 07-22 22:33에서 멈춰 있다.
**파일 시각과 내용 시각을 섞어 읽으면 사고가 3.5일 뒤로 밀린다.**

📌 **`.fuse_hidden*` 23개가 §5의 핵심 단서다.** 32,768바이트 · 헤더 매직 `18e2 2d00` —
**SQLite `-shm`(WAL-index) 파일**이고, 실제 `ohlcv.db.corrupt.bak-shm`과 같은 매직을 쓴다.
`.fuse_hidden*`은 **FUSE 파일시스템이 「열려 있는데 삭제된」 파일에 붙이는 이름**이다.
birth가 전부 **01:09:01**(= `corrupt.bak` 복사 시작과 같은 초)이다.

읽을 수 있는 것은 두 가지다:

1. **01:09에 `data/` 위에 FUSE 파일시스템이 마운트돼 있었다**(지금은 아니다 — `mount`에
   FUSE/네트워크 항목이 없고 `df`는 로컬 `/dev/disk3s1`을 가리킨다). **§1의 명시 질문
   "로컬 `data/`가 서버 마운트인지"의 답: 지금은 아니지만, 그 시점엔 마운트였다.**
2. **SQLite 연결 23개가 그 DB들을 동시에 열고 있었다** — `-shm`은 연결이 있을 때만 산다.

🚨 **SQLite를 FUSE·네트워크 파일시스템 위에서 여러 연결로 돌리는 것은 손상의 교과서적
벡터다** — advisory locking이 정확히 동작하지 않아 WAL 인덱스가 깨진다. WAN-194가 유력
벡터로 꼽은 "07-24 쓰기 도중 강제종료"는 **시각이 안 맞는다**(복구는 07-22 22:38이고 07-24는
그 뒤다). 아래 §5가 이 축을 서버에서 확인할 항목으로 바꿔 둔다.

⚠️ **이 판정의 한계** — 전부 **로컬 파일**의 증거다. 서버에서 `.recover`를 누가 언제 쳤는지는
`~/.bash_history`·`journalctl`에만 있고 이 세션은 서버에 못 붙는다(§2·§5는 대기).
다만 **서버 DB와 이 로컬 DB는 `lost_and_found` 행 수가 2,827,970으로 정확히 같아** 같은
복구 산출물 계보임이 확인된다.

## 2. §4-1 — `lost_and_found` 안에 무엇이 있나

`.recover`는 고아 행이 **어느 테이블 것인지**를 잃고 필드 개수와 값만 남긴다. 그래서
행 수만 세면 "283만 행 쓰레기"로 보인다. 분해하면 두 모양뿐이다:

| 모양 | 행 수 | 정체 |
| -- | --: | -- |
| 9필드 `(text, text, int, num×5)` | 1,450,217 | **`ohlcv` 캔들 행**(9열과 일치) |
| 4필드 `(text, text, int, int)` | 1,377,753 | `ohlcv` PK **인덱스 조각** |

그 캔들을 타임프레임으로 갈랐더니:

| TF | 고아 행 | 심볼 | 기간 | 살아 있는 `ohlcv` | 판정 |
| -- | --: | --: | -- | --: | -- |
| `5m` | **1,450,185** | 6 | 2023-07-11 … 2026-07-18 | **0** | 🚨 **유일본** |
| `1m` | 32 | 1 | — | 28,306,532 | 중복(버려도 됨) |

🚨 **살아 있는 `ohlcv`에 5m은 0행이다.** 즉 **5m 데이터셋 전체가 이 산출물 안에만 있다.**
이것은 알려진 사실과 맞물린다 — 5m은 2026-07-19에 백필됐다가 "손상 사고로 사라졌다"고
기록돼 있었는데, **사라진 게 아니라 `lost_and_found`에 갇혀 있었다.**

복원 후 품질 검사도 통과했다(1,445,500행 · 6심볼 · `high<low` 0 · OHLC 범위 위반 0 ·
음수 거래량 0 · 5분 정렬 위반 0 · `closed<>1` 0).

## 3. §4-2 — 매매 장부는 왜 복원할 수 없나 (「없다」가 아니라 「담길 수 없다」)

`.recover`는 **가장 넓은 고아 행에 맞춰** `c0..cN` 열을 만든다. 이 DB의 `lost_and_found`는
**`c0..c8` = 9열**이고, 실측 `MAX(nfield)`도 **9**다. 그런데:

| 테이블 | 열 수 | 담길 수 있나 |
| -- | --: | -- |
| `ohlcv` | 9 | ✅ (실제로 담겨 있다) |
| `open_positions` | 10 | ❌ |
| `paper_trades` | **17** | ❌ |
| `live_limit_orders` | 20 | ❌ |

📌 **이것이 "찾아봤는데 없더라"보다 훨씬 강한 진술이다** — 9필드보다 넓은 행은 **구조적으로**
이 산출물에 들어갈 수 없다. 그러므로 **§4의 「매매 기록 복원 시도」는 부정으로 닫힌다**:
`lost_and_found`에서 나올 매매 기록은 없다. (`bull`/`bear` 방향 문자열 검색도 0건으로 교차
확인했다.) 코드가 이 논증을 그대로 낸다 — `RecoveryArtifactCensus.could_contain()`.

📌 **그럼 매매 장부는 어디서 오나** — 로컬 `ohlcv.db`(및 `corrupt.bak`)에 **`paper_trades` 2행이
살아 있다**(BTC/USDT 1h, 07-13 12:00 손절 · 07-14 02:00 익절). 서버 DB는 이 2행을 잃었으므로,
복원을 원하면 **로컬 스냅샷이 유일한 소스**다. ⚠️ 다만 이 2행은 **07-14까지의 기록**이고
그 이후 페이퍼 거래는 어느 사본에도 없다(`open_positions`는 세 파일 모두 0행).

## 4. 고친 것 (코드)

§1·§4의 판정은 문서로 끝나지만, **그 판정을 낸 도구가 없으면 다음 사고에서 또 반나절이
간다**. 그리고 WAN-194가 남긴 도구에는 **실제 위험**이 있었다.

🚨 **`alphablock doctor --drop-recovery-artifacts`는 5m 145만 행을 말없이 지웠을 것이다.**
행 수만 보고 "쓰레기"로 판단하게 만드는 리포트 + 무조건 드롭하는 명령의 조합이었다.
드롭은 되돌릴 수 없다(그 DB에만 있는 유일본이다).

* **`data.integrity.census_recovery_artifacts()`** — 산출물 **안**을 TF별로 분해하고, 각
  묶음이 살아 있는 `ohlcv`에 있는지 대조해 **「유일본」과 「중복」을 가른다**. `doctor`
  리포트가 드롭 명령을 안내하기 **전에** 이 표를 낸다.
* **`RecoveryArtifactCensus.could_contain(arity)`** — §3의 열 수 논증. 리포트가
  "`paper_trades`(17열)의 행은 **있을 수 없다**"를 문장으로 찍는다.
* **`salvage_ohlcv()` / `alphablock doctor --salvage-ohlcv [TF…] [--dry-run]`** — 갇힌 캔들을
  `ohlcv`로 되돌린다. 인자가 없으면 **사라진 TF만** 복원한다. **기존 행은 절대 덮어쓰지
  않는다**(`ON CONFLICT DO NOTHING`) — 거래소에서 받은 봉이 복구 산출물로 조용히 바뀌면
  그게 더 나쁜 사고라, 충돌은 언제나 살아 있는 쪽이 이긴다(WAN-175 백필 규약과 같다).
* **드롭 가드** — 유일본이 남아 있으면 `SalvageableRowsPresent`로 **거부**하고 종료 코드 1을
  낸다. 버릴 것이 확실하면 `--force`. 오타 TF는 조용히 0건이 아니라 `ValueError`다
  (「복원했다」고 믿게 만드는 실패를 막는다 — WAN-91/95/112 부류).

기존 CSV·리포트는 **비트 단위로 재현된다**(`--salvage-ohlcv`를 안 주면 쓰기 경로가 없다).
회귀 테스트가 **라벨이 아니라 동작**으로 고정한다: 유일본이 실제로 남는지, 살아 있는 값이
안 덮이는지, dry-run이 정말 안 쓰는지, 인덱스 조각이 `ohlcv`로 흘러들지 않는지.

📌 **실행 결과(로컬 스냅샷 복사본에서 실측)**: `5m` 후보 1,450,185행 → **삽입 1,445,500행**
(중복 4,685행은 건너뜀 — 복구 페이지에는 같은 행의 옛 판이 섞여 있다). 복원 후에는 5m이
더 이상 유일본이 아니므로 드롭 가드가 자동으로 풀린다.

⚠️ **이 저장소의 `data/ohlcv.db`에는 아직 복원을 돌리지 않았다** — 그 파일은 §1의 증거이고,
복원 대상은 **서버 DB**다(아래 런북). 검증은 전부 **복사본**에서 했다.

## 5. §2·§5 — 서버에서 할 일 (이 세션은 SSH가 없다)

`rocky@orderblock`은 이 세션에서 이름이 풀리지 않고(`orderblock.local`은 다른 호스트로
풀려 22번 포트가 타임아웃) 접근이 없다. 그래서 **판단을 코드로 옮기고 실행만 넘긴다.**

```bash
./scripts/wan195-server-forensics.sh -o wan195-evidence.md
```

읽기 전용 수집이다(삭제·VACUUM·복구 없음). 모으는 것: 파일 birth/mtime · `.bash_history`의
`.recover`/`.dump`/`reindex` · `journalctl`의 `malformed|corrupt|SIGKILL|oom` · **`mount`의
FUSE/네트워크 항목**(§1이 지목한 축) · 디스크 여유 · WAL 크기·체크포인트 · `doctor` 전문 ·
LINK 15m 체결의 `entry_status`.

### 5-1. LINK 건 분류 (§2)

배포·러너 재시작 후 `entry_status`가 채워진다. `rejected`(+사유)면 **정상 거부**(손절폭 가드
0.3%)이고, `NULL`이면 **판별 불가**(WAN-194 이전 기록) 또는 **진짜 유실**이다. 창을 자르려면
`--orphans-since 2026-07-26`.

### 5-2. `lost_and_found` 처분 런북 (§4) — ⚠️ 사용자 결정

```bash
uv run alphablock doctor --skip-quick-check            # 1. 무엇이 갇혔는지 먼저 본다
uv run alphablock doctor --salvage-ohlcv --dry-run     # 2. 복원 대상 확인(쓰기 없음)
uv run alphablock doctor --salvage-ohlcv               # 3. 5m 복원
uv run alphablock doctor --drop-recovery-artifacts     # 4. 그 뒤에야 드롭이 통과한다
# 5. VACUUM은 러너·수집기를 멈추고 사람이 — DB 독점 락 + 같은 크기 임시 파일
```

🚨 **순서를 지킬 것.** 3을 건너뛰고 4를 치면 가드가 거부한다(그게 이 PR이 넣은 안전장치다).
**VACUUM은 자동화하지 않았다** — 3.8GB DB를 독점 락하므로 러너 정지가 선행이고, 그건
사용자 결정이다.

### 5-3. 재발 방지 (§5) — ⚠️ 운영 결정, 임의 등록 금지

* 📌 **최우선: DB를 FUSE/네트워크 마운트 위에서 돌리고 있지 않은지 서버에서 확인**(§1).
  그렇다면 그것이 원인이고, 로컬 디스크로 옮기는 것이 유일한 진짜 수정이다. WAN-194가
  꼽은 "07-24 강제종료"는 **복구 시각(07-22 22:38)보다 뒤라 원인일 수 없다.**
* `doctor`는 이상이 있으면 **종료 코드 1**이라 cron·감시에 그대로 물릴 수 있다(3.5GB 실측
  12초). **다만 cron 등록은 이슈가 명시적으로 금지했으므로 하지 않았다** — 등록 여부는
  사용자 결정이고, 명령은 위 런북에 있다.
* 백업 회전도 **제안만 한다**(서버에 `.bak`/`.old`가 없다는 것이 WAN-194 census의 관찰이다).

## 6. 범위 밖 (명시)

기본값·토대 **불변**(오프셋 2bp · `intrabar_live` · `unconditional` · 고정 1.5R · 롱 온리 ·
`combine_obs=False` · 존폭 1.28) · **손절폭 가드 0.3%는 손대지 않았다**(WAN-76/79 소관) ·
실거래 보류 유지(`ALPHABLOCK_LIVE_TRADING=false`) · 5m 복원이 백테스트 좌표를 바꾸지
않는다(채택 TF는 15m·1h·4h이고 5m은 어느 리포트도 읽지 않는다) · 서버 실행·VACUUM·cron
등록은 **사용자 몫**이다.
