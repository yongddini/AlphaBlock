# WAN-344 — 러너 정지 감시를 등록한다 (§4 · §1~§3은 조사로 닫힘)

**판정 한 줄**: 재시작 10회는 **크래시가 아니었다**(§1~§3). 진짜 문제는 그 조사 중에 나온
것 — **러너 정지를 아는 유일한 장치(`alphablock watch`)가 서버 어디에도 등록돼 있지
않았다.** 이 PR 이 그것을 systemd 타이머로 등록하고, 「경보가 안 가는데 그 사실도 경보되지
않는」 자리를 종료 코드로 막는다.

운영·도구 전용 — **전략·엔진·기본값·토대 불변**(`ConfluenceParams()`·`LeverageBookParams()`
그대로) · **DB 에 아무것도 쓰지 않는다**(WAN-194) · 실거래 보류 유지
(`ALPHABLOCK_LIVE_TRADING=false`).

## §1~§3 — 이미 닫힌 조사 (이 PR 의 근거이자 범위 밖)

이슈 본문 상단 재정의와 코멘트가 서버 실측으로 냈다. 재인용용으로만 옮긴다:

| 질문 | 답 |
| -- | -- |
| §1 재시작 10회는 크래시인가 | **아니오** — 크래시 증거가 앱 로그·journald·커널 로그 **세 축 전부 0**. 08-20 12:42 정지도 `Deactivated successfully`(정상 SIGTERM). 그 기간 배포 다수(08-18 WAN-297/325 · 08-20 WAN-339/326/337). |
| §2 34·41분 공백의 원인 | **(b) 사람이 정지 후 늦게 시작** — `Restart=always`/`RestartSec=10` 은 **정상 정지에는 재시작하지 않는다**. 후보 (a) 시작 속도 제한(`Start request repeated too quickly`)의 흔적은 없었다. |
| §3 그동안 경보가 갔는가 | **안 갔다** — 다만 이유가 WAN-321(텔레그램 출구 막힘)이 아니라 **감시 자체가 안 돌고 있었기 때문**이다. |

🚨 **그래서 유닛 설정을 손대지 않았다**(이슈 「원인 확정 전 변경 금지」). `Restart`·
`StartLimitIntervalSec`·`StartLimitBurst` 전부 그대로다 — 원인이 크래시가 아닌데 재시작
정책을 늘리면 증상만 가린다.

## §4 — 감시 등록 (이 PR)

### 1. 유닛 두 개 신설 — 타이머 + oneshot

`scripts/systemd/alphablock-watch.{service,timer}.template`. 타이머가 기본 **10분**마다
`alphablock watch --once --require-delivery` 를 돌린다(`ALPHABLOCK_WATCH_INTERVAL`).
기본 10분은 설정 기본값 `health_watch_interval_seconds`(600초)와 **같은 값**이다.

📌 **상주 service 가 아니라 timer + `--once` 인 이유 둘**:

1. 쿨다운·복구 상태가 `health_watch_state_path`(JSON)로 **이미 영속화**돼 있다 — 매번 새
   프로세스로 돌아도 중복 경고가 나지 않는다(WAN-32 설계, 회귀 테스트가 동작으로 고정).
   즉 이슈 §4-3 「쿨다운 확인」의 답은 **「타이머로 돌려도 안전하다」**이다.
2. 상주 프로세스는 **죽으면 그 사실을 알 장치가 또 필요하다**(감시의 감시). 타이머는
   프로세스가 죽어도 다음 주기에 그냥 다시 뜬다 — doctor 와 같은 패턴이고, 이슈가 제안한
   방향이기도 하다.

부팅 오프셋은 doctor(5min)·doctor-light(10min)와 어긋나게 **2min** 에 뒀다(부팅 직후 셋이
동시에 디스크를 물지 않게 · 「무엇이 안 뜬다」를 가장 먼저 알아야 하므로 가장 앞).
점검은 가볍다(Health 뷰 = 시리즈별 최신 봉 조회 + 하트비트 파일 읽기) — doctor 와 달리
「주기 < 실행 시간」 위험이 없다. 그래도 `Nice=19` · `IOSchedulingClass=idle` 로 수집기·러너에
디스크를 양보한다(WAN-318 §1).

### 2. 설치·해제 스크립트에 배선

`install-systemd.sh watch` / `uninstall-systemd.sh watch` + **`all` 에 포함**. 회귀 테스트가
`all` 분기의 **실제 호출**로 잠근다 — 라벨이 아니라 동작으로(이 이슈의 본문이 정확히 「목록에
없어서 안 돌았다」이므로).

### 3. 🚨 「감시는 도는데 아무 데도 안 가는」 상태를 실패로 만든다 — `--require-delivery`

새 옵트인 플래그(`alphablock watch --require-delivery` · `run_health_watch(require_delivery=)`).
종료 코드: **0** 정상 · **1** 전송 실패 · **2** 텔레그램 미설정.

이게 없으면 텔레그램이 미설정일 때 워치가 **조용히 드라이런으로 접고 0을 낸다** — systemd 에서
성공으로 보인다. WAN-321 이 고친 실패 부류(경보가 안 가는데 그 사실도 경보되지 않음)와 정확히
같은 자리다. 그래서 이 유닛에는 doctor 와 같은 이유로 **`SuccessExitStatus` 를 넣지 않는다**
(넣으면 `systemctl --failed` 감시가 조용히 죽는다).

⚠️ **기본 동작은 안 바뀐다** — `--require-delivery` 없이는 예전처럼 미설정 시 드라이런으로
돌고 0을 낸다. 딱 하나 바뀐 것이 **`--test-message`** 다: 실패해도 0을 내던 것을 1/2 로
바꿨다. **연결 확인이 실패했는데 0을 내면 그건 확인이 아니다**(이슈 §4-4).

### 4. 부수 수리 — 전송 실패가 쿨다운을 걸고 있었다

`apply_delivery_failures()`(순수 함수) 신설. 옛 동작은 `reconcile` 결과를 그대로 저장해
**전송이 실패해도 「방금 보냄」으로 기록**했다 → 그 뒤 쿨다운(기본 1시간) 동안 **재시도조차
하지 않는다**. 실패한 것만 이전 상태로 되돌린다:

* 실패한 **첫 경고**: 기록을 지운다 → 다음 점검에 새 경고로 다시 나간다.
* 실패한 **리마인더**: 옛 타임스탬프를 유지한다 → 쿨다운이 이미 지났으므로 즉시 재시도.
* 실패한 **복구 알림**: 기록을 되살린다 → 다음 점검에 다시 복구로 잡힌다.

WAN-321 의 평문 폴백이 서식 실패를 구제하지만 네트워크 실패는 남는다 — 그때 한 시간을 침묵하는
것이 옛 동작이었다. 회귀 테스트가 「실패 → 쿨다운 이내인데 재시도」로 고정한다.

## 남은 것 — 서버에서 사람이 한 번 (이 세션엔 SSH 없음)

```bash
cd ~/AlphaBlock && git pull
./scripts/install-systemd.sh watch
uv run -- alphablock watch --test-message; echo "종료 코드: $?"   # 🚨 폰에 오는지
systemctl list-timers alphablock-watch.timer --no-pager
```

절차·해석표는 [`docs/ops/wan344-runner-watch.md`](../ops/wan344-runner-watch.md).
**등록만 하고 도착을 안 보면 같은 자리다.**

## 부수 발견 — journald 보존 3시간 (별도 조각)

`journalctl -u alphablock-live` 의 가장 오래된 기록이 3시간 전이라 **과거 재시작 원인을
journald 로는 조사할 수 없었다**(이슈 §1·§2 의 방법이 그래서 막혔다). 유닛의
`StandardOutput=append:` 파일 로그 덕분에만 과거를 봤고, 새 워치 유닛도 같은 규약으로
`logs/watch.log` 를 남긴다. `journald.conf`(`Storage`·`SystemMaxUse`) 조정이나 rsyslog
이중화는 **이 PR 범위 밖**이다(런북에 확인 명령만 적어 뒀다).
