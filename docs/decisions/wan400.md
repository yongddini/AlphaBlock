## §1 A — 소멸 존 제외: **이슈의 전제가 틀렸다**

이슈는 *"원본은 소멸한 존을 겹침 판정에서 빼지 않습니다 — 리스트에 남아 `breakTime`을
오른쪽 변으로 계속 참여합니다"*라고 적었고, 「먼저 조사할 것」으로 *「우리 `swept_time`이
원본의 무엇에 대응하는가 · `box.delete()`가 렌더링에서만 지우는가」*를 남겼다.

**답: 원본은 데이터 리스트에서 뺀다.** `.pine:260-267`(강세 · 약세 `:301-308` 대칭):

```pine
if not currentOB.breaker
    if (obEndMethod == "Wick" ? low : math.min(open, close)) < currentOB.bottom
        currentOB.breaker  := true
        currentOB.breakTime := time
else
    if high > currentOB.top
        bullishOrderBlocksList.remove(i)      // ← 데이터 리스트에서 제거
```

그리고 그 리스트가 곧 병합 입력의 **원천**이다(`handleOrderBlocksFinal`, `.pine:425-452`):
`allOrderBlocksList.clear()` → `curTimeframe.bullishOrderBlocksList`에서 복사 →
`combineOBsFunc()`가 그 `allOrderBlocksList`만 훑는다. **즉 원본에서도 소멸 존은 겹침
판정에 참여하지 않는다.**

📌 **우리 조건도 글자 그대로 같다** — `_invalidate()`가 breaker 상태에서 강세는
`highs[t] > ob.top`, 약세는 `lows[t] < ob.bottom`일 때 `swept`로 넘긴다. 원본의
`remove(i)` 조건과 **같은 부등식**이다.

📌 **`box.delete()`는 다른 것이다** — `safeDeleteOrderBlock`은 `handleOrderBlocksFinal`이
매 봉 렌더를 처음부터 다시 그리려고 부르는 **렌더 정리**이고, 소멸과 무관하게 **모든**
박스에 걸린다. 우리 코드 주석이 이것을 소멸 처리라고 적어 두어 이슈의 오독을 낳았다 —
`strategy/order_blocks.py`·`strategy/models.py`의 그 주석을 정정했다.

### 판정: **현행 유지** (코드 변경 없음)

「원본과 맞춘다」고 소멸 존을 후보에 남기면 **원본에서 멀어진다**. 그래서 아무것도 안
바꿨고, 대신 **판정 자체를 테스트로 못 박았다** — `test_pine_removes_swept_zone_from_the_
data_list_not_only_the_box`가 원본 파일에서 그 사슬(제거 → 리스트가 병합 입력 → 병합이
그 리스트만 훑음)을 읽어 확인한다. 같은 오독이 다시 나오면 테스트가 먼저 걸린다.

⚠️ **아카이브 보존은 이 판정과 무관하다** — 우리 탐지 아카이브(`OrderBlock`)가 소멸 존을
지우지 않는 것은 생존자 편향을 없애려는 WAN-47 확장이고(원본은 백테스트를 하지 않는다),
**병합 후보 집합**은 `_generate_merged_signals`가 소멸 존을 빼서 원본과 맞춘다. 두 층을
섞지 말 것.

### 크기 (§0 A 팔 — 「이슈 전제대로 고쳤다면」)

36칸(1h·2h·4h · 그 칸들의 기준 탭 57,746건)에서 소멸 존을 **안 뺐다면**:
**없어진 탭 4,319 · 새로 생긴 탭 3,660 = 7,979건이 달라진다(13.82%)**. 순변화는
−1.14%로 작지만 그건 상쇄된 값이고, **여덟 탭 중 하나가 다른 탭이 된다.** 방향도
칸마다 갈린다(칸별 −3.03% ~ +1.68% · 36칸 중 4칸은 오히려 탭이 는다).

📌 **즉 이 자리를 「고쳤다면」 병합 경로의 탭이 14% 뒤집혔을 것이다** — 원본을 읽지
않고 이슈 전제대로 갔으면 **원본과 다른 엔진을 「원본과 같게 고쳤다」는 이름으로**
들고 있었을 것이다. 소멸 존은 전체 존의 **95.64%**(100,553개 중 96,165개)라 이 축이
작을 수가 없다.

⚠️ **15m은 안 쟀다** — 이 팔은 아무것도 안 죽는 반사실이라 활성 집합이 창 끝까지 커져
비용이 초선형이다(BTC 실측 1h 57.9초 vs B 4.2초 · C 6.1초). **틀린 것으로 판명된
전제의 크기**를 재는 팔이고 **A 판정은 이 팔이 아니라 원본 소스 대조에서 나온다.**

## §2 B — `break_time` 산정: ✅ 사용자 결정 = 현행 `distal` 유지

### 두 규칙

| | 규칙 |
| -- | -- |
| **원본** (`.pine:391-392`) | `newOB.breakTime := math.max(nz(A.breakTime), nz(B.breakTime))` → `== 0 ? na` |
| **우리** (`_make_merged_group`) | `break_time = distal.break_time` (합집합 경계를 정의하는 존) |

🚨 **원본 규칙의 실제 의미는 「늦게 죽는 쪽」이 아니다.** `nz(na) = 0`이고 실제 시각은 항상
양수이므로, 이 접기는 다음과 **정확히 같다**(병합 순서·구성원 수와 무관):

* 구성 존이 **전부 살아 있으면** 병합 존도 살아 있다.
* **하나라도 죽었으면** 병합 존은 **죽은 것들 중 가장 늦은 시각**에 죽는다 —
  **아직 살아 있는 구성 존이 있어도 그렇다**(살아 있는 쪽이 최댓값을 못 올린다).

즉 원본은 우리보다 **더 잘 죽이는** 방향일 수도, **덜 죽이는** 방향일 수도 있다:

| 상황 | 우리(`distal`) | 원본(`pine_max`) |
| -- | -- | -- |
| distal이 먼저 죽고 다른 존이 나중에 죽음 | 먼저(=distal 시각) | **나중** |
| distal은 살아 있고 다른 존만 죽음 | **살아 있음** | 죽음(그 존 시각) |
| 전부 살아 있음 | 살아 있음 | 살아 있음 |

두 반례 모두 회귀 테스트로 고정했다.

### 🚨 정정 — 「덜 죽이는 경우」는 물리적으로 불가능하다

이 PR의 초판 보고(그리고 이슈 §2)가 *"우리보다 **더 잘 죽이는 경우와 덜 죽이는 경우가
둘 다** 있다"* 고 적었는데, **사용자 지적대로 뒤쪽은 어떤 가격 경로로도 만들 수 없다.**
강세 기준 증명(약세 대칭):

* A를 distal(`bottom` 최저), B를 같은 클러스터의 다른 구성 존(`bottom_B > bottom_A`)이라
  하자. A가 `t_A`에 깨지면 `low(t_A) < bottom_A < bottom_B`다.
* **B가 `t_A`에 이미 확정돼 있었다면** 같은 봉이 `bottom_B`도 뚫으므로 B는 `t_A` 이전이나
  같은 봉에 깨진다 → 「B가 더 늦게」가 불가능하다.
* **B가 `t_A` 뒤에 확정됐다면** 탐지기가 B의 `bottom`을 형성 창의 **최저 저가**로,
  `start_time`을 **바로 그 봉**으로 잡는다(`_create_bullish` ≡ 원본 `boxBtm`/`boxLoc`).
  그러면 `t_A`가 창 **안**이면 `bottom_B <= low(t_A) < bottom_A`라 **B가 distal**이 되고
  (가정 위배), 창 **밖**이면 `start_time_B > break_time_A`라 `obs_touch` 시간축 교집합이
  음수가 되어 **애초에 같은 클러스터가 아니다**.

📌 **그래서 두 규칙의 실제 차이는 하나뿐이다** — *「위쪽 존만 깨진 상태에서 계속 진입할
것인가」*. 실측이 그 방향을 뒷받침한다(§0 B: 없어진 탭 6 · **새로 생긴 탭 0**).

| 경우 | `distal` | `pine_max` | |
| -- | -- | -- | -- |
| 위쪽만 깨짐 | 안 죽음 | 죽음 | 🚨 **여기만 다름** |
| 둘 다 깨짐 | distal 시각 | `max` = distal 시각 | 같음 |
| ~~밑단 먼저, 위쪽 나중~~ | | | ❌ **불가능** |

⚠️ 회귀 테스트(`test_pine_max_folds_to_the_latest_death_on_a_configuration_price_cannot_
produce`)는 그 불가능한 배치를 **`break_time`을 직접 심어** 만든다 — **접기 규칙의 단위
테스트일 뿐**임을 이름과 독스트링이 밝힌다.

### ✅ 결정: 현행 `distal` 유지 (사용자 결정 2026-09-01)

사용자 원문: *"병합이 됐는데 밑단 윗단이 중요해? 그냥 105-95, 100-90 합쳐지면 (…) 100
부근에 진입하고 90 밑에 손절하고 그러는거 아니야?"* → *"일단 B는 현행 유지해"*.

| | 무엇을 보고 병합 박스를 죽이나 |
| -- | -- |
| **현행 `distal`**(채택) | **병합 박스 자체** — 밑단이 뚫리면 죽음 |
| 원본 `pine_max` | **구성 존 개별** — 위쪽 존이 깨지면 박스는 멀쩡한데도 죽음 |

📌 `distal`은 「밑단을 정의하는 존」이고 **그 존이 깨진다는 게 곧 「가격이 병합 박스의
밑단 아래로 갔다」**이다. 즉 `distal` 규칙 = *"합쳐진 박스의 밑단이 뚫리면 죽는다"* 이고
그게 **손절선과 정확히 같은 선**이다. 원본은 **박스를 그리는 도구**라 구성원 단위 관리로
충분하지만, 우리는 **그 박스로 매매하고 손절선이 밑단**이다.

🚨 **즉 「pine 소스랑 동일하게」에서 이 한 축만 의도적으로 다르게 간다.** 알고 고른 것이다.

`merged_break_time_rule="pine_max"` 옵트인은 **존치**한다(나중에 비교하고 싶을 때 —
WAN-128이 `pen_5bp`를 남긴 것과 같은 처리).

🚨 **`break_time`은 `obs_touch`의 오른쪽 변**이라(`.pine:347`·`:352` / `models.obs_touch`)
바꾸면 **겹침 판정 결과까지** 달라진다 — 「존이 언제 죽나」만 바뀌는 게 아니라 **어느
존들이 한 클러스터가 되는가**가 바뀐다.

### 배선

`OrderBlockParams.merged_break_time_rule: Literal["distal", "pine_max"] = "distal"`.
**기본값 불변 · 안 주면 비트 재현.**

### 크기 (§0 B 팔)

**규칙이 갈리는 클러스터는 있는데, 탭은 거의 안 움직인다.**

* 기준 팔 탭 195,498건 중 **병합이 무는 탭**(구성 존 2개 이상)이 36,554건(18.70%).
* 그중 두 규칙의 `break_time`이 **다른** 클러스터에서 난 탭이 **307건**
  (병합 탭의 **0.84%** · 전체의 0.16%). 칸별 0.00% ~ 5.61%.
* 그런데 팔을 실제로 돌리면 **없어진 탭 6 · 새로 생긴 탭 0**(48칸 중 6칸에서 각 1건).
  전체 탭의 **0.003%**다.

📌 **읽는 법**: 규칙은 실재하는데 **관측 가능한 결과가 거의 없다.** 병합 존의 수명이
달라지는 순간이 대체로 「그때 가격이 탭하지 않는」 구간이고, `obs_touch`의 문턱이
IoU > 0이라 오른쪽 변이 조금 움직여도 겹침 판정이 잘 안 뒤집히기 때문이다.

⚠️ **「그러니 아무 쪽이나 골라도 된다」로 읽지 말 것** — 이 표는 **탐지 층의 탭**만
센다. 병합 존의 `break_time`은 진입 후보의 유효 창(`in_window`)이자 손절선의 근거이므로,
**손익 축은 안 쟀다**(그건 북에서 재야 한다 — WAN-341). 다만 **선택의 비용이 크지
않다**는 것까지는 이 표가 말한다.

## §3 C — 탭 상태 키: 우리가 설계하는 자리

### 결함

```python
was_inside = inside_state.get(g.member_indices, False)   # 키 = 그 시점 구성 존 집합
```

클러스터 구성이 바뀌면 키가 달라져 「직전 봉에 안에 있었다」 기록이 **리셋**된다. 그러면
가격이 **한 번도 밖으로 나가지 않았는데** 새 탭이 난다. 대표 경로는 이 저장소가 원본과
같게 유지하는 바로 그 동작이다 — **구성 존 하나가 소멸해 클러스터가 줄어드는 봉**(§1).
📌 **소멸만이 아니다** — 구성 존이 **무효화**되면 그 존의 오른쪽 변이 `now`에서
`break_time`으로 **줄어들어** 시간축 교집합이 사라질 수 있고, 그러면 겹쳐 있던 클러스터가
**쪼개진다**(`obs_touch`). 그래서 이 결함은 소멸이 드문 칸에서도 난다.

🚨 **재탭 「번호」도 되돌아간다** — 구성이 바뀌면 `retap_counter`도 새 키가 되어 다음
재탭이 **1번부터** 다시 세어진다. `tap_index`는 재탭 정책이 소비하는 값이라(WAN-81/123)
이건 라벨이 아니라 **동작**이다. 반례:

| 봉 | t2 | t4 | t6 | t8(구성 변경 뒤) |
| -- | --: | --: | --: | --: |
| 현행 `cluster` | 0 | 1 | 2 | **1** ← 리셋 |
| `zone` | 0 | 1 | 2 | **3** |

⚠️ 부수 위험 둘: (1) 같은 구성이 나중에 다시 나타나면 **낡은 값이 되살아난다**,
(2) `inside_state`·`retap_counter`가 **정리되지 않고 계속 쌓인다**.

📌 **원본에는 대응물이 아예 없다** — 원본은 탭·재탭·`entered`를 세지 않고 박스만 그린다.
탭 카운팅은 전부 우리 확장(WAN-56/81/82)이라 **「원본과 동일하게」가 정의되지 않는다.**

### ✅ 사용자 결정 (2026-09-01) — 「존만 넓어지는 것」은 새 기회가 아니다

> *"새롭게 존이 병합하는 경우는 새로 탭을 셀 필요가 없지. 단순히 존만 넓어지는거야"*
> *"기회를 안주는게 맞지"*

**규칙**: 직전 봉에 가격이 그 박스(그 시점 구성) 안에 있었으면, **구성이 바뀌어도
「안에 있었다」로 본다.** 병합된 것은 **하나의 박스**이고 커져도 같은 박스이므로,
**가격이 안 움직였으면 새 진입 기회가 아니다.**

### 구현 (`merged_tap_state="zone"`)

상태를 **아카이브 존 인덱스마다** 들고, 그룹의 값을 구성 존들에서 접는다:

* 「직전 봉에 안에 있었다」 = **구성 존 중 하나라도 그랬는가**(`any`)
* 재탭 카운터 = 구성 존들의 **최댓값**에서 이어 센다(병합·분리로 1로 안 돌아간다)

### 🚨 WAN-82를 되돌리는 것이 아니다 — 두 자리를 갈랐다

| 상황 | 처리 |
| -- | -- |
| **가격이 계속 박스 안에 있는데** 구성이 바뀜 | ❌ 탭 **안 셈** ← 이번 결정 |
| **가격이 밖으로 나갔다가 다시 들어옴** | ✅ 탭 세고, `member_indices - entered`로 미진입 구성 존에 기회 |

📌 **WAN-82의 원래 문제는 뒤쪽**이었다 — *"이미 진입한 클러스터에 새로 편입된 존까지
**영구적으로** 진입 기회를 잃었다"*. 가격이 다시 들어올 때 그 존이 기회를 갖는 것은
**그대로**이고, 이번 결정은 「가격이 안 움직인 동안에는 기회를 만들지 않는다」까지다.
**두 시나리오를 각각 회귀 테스트로 못 박았다** — 하나만 고정하면 나머지가 조용히 무너진다.

📌 **이 팔은 탭을 늘리지 않는다(단조)** — `any`는 `all`보다, `all`은 `cluster`보다 항상
덜 센다. 인구조사가 매 칸에서 그 성질을 확인하고 깨지면 죽는다.

⚠️ **개발자 초안(`all`)은 `merged_tap_state="zone_all"`로 존치**한다 — **측정 대조 전용**
이고(두 규칙의 차이 = 이번 결정의 크기) **새 측정에 쓰지 않는다**. 초판 보고가 *"`any`로
접으면 WAN-82가 무너진다"* 고 적었는데, 위 표대로 **자리를 나누면 무너지지 않는다.**

### 판정: **사용자 결정 규칙을 옵트인으로 싣고 기본값은 유지** — 전환은 별도 재-베이스라인

⚠️ **기본값 전환 여부는 이 PR 범위 밖이다**(PM 변경요청 명시). `cluster`가 결함이라는 것은
위 논증과 실측으로 서지만, **기본값을 지금 뒤집지 않은 이유가 셋**이다:

1. **채택 경로가 이 값을 안 읽는다** — `combine_obs=False`(WAN-149)라 병합 경로가 안 돈다.
   즉 뒤집어서 **당장 나아지는 숫자가 없다**.
2. **뒤집으면 옛 병합 리포트가 통째로 움직인다** — `harness.LEGACY_COMBINE_OBS`(= `True`)로
   병합을 명시 고정한 리포트들은 **병합 경로를 실제로 돈다.** 기본값을 바꾸면 그 표들이
   조용히 새 탭 집합으로 다시 돌아 본문과 어긋난다(WAN-149/159/365가 매번 치른 파급).
   그 대가를 치를 근거가 **옵트인 경로의 정확성뿐**이다.
3. **이 값을 필요로 하는 이슈는 명시하면 된다** — 이 이슈가 막고 있는 **WAN-374**(병합
   재측정)는 `merged_tap_state="zone"`을 **명시해서** 돌리면 결함 없는 병합 팔을 얻는다.
   기본값을 안 건드리고도 목적이 달성된다.

📌 **권고**: 앞으로 **새로** 내는 병합 측정은 `merged_tap_state="zone"`을 명시한다(옛
리포트는 그대로 둔다 — 그때의 기록). 기본값 전환을 원하면 **별도 재-베이스라인 이슈**로
하고, 그때 `LEGACY_MERGED_TAP_STATE` 핀을 함께 단다.

### 크기 (§0 C 팔 · ★ 결정의 크기)

**없어진 탭 3,683 · 새로 생긴 탭 0**(전체 탭의 **1.88%**). 예측대로 **단조**이고
**48칸 전부 음수**다(칸별 −1.09% ~ −2.70% · 새로 생긴 탭은 48칸 전부 0).

#### ★ 결정이 없앤 「합류 탭」 — 초안(`all`)이 세던 것

| | 건수 | 기준 팔 대비 |
| -- | --: | --: |
| 「구성 변경 + 가격은 계속 안에」로 세던 탭 | **716** | 0.37% |
| 그중 **첫 탭** | **378** | 0.38% |

47칸(48칸 중)에서 나오고 칸당 최대 74건이다. TF별: 15m 520 · 1h 109 · 2h 52 · 4h 35.

🚨 **이 결정은 「첫 탭」도 움직인다 — 초안(`all`)과 여기서 갈린다.** `all`의 순변화는
첫 탭에서 +0.00%였는데(가짜 탭이 대부분 **재탭**으로 샜다) 이번 규칙은 **−0.38%**다.
「가격은 안에 있는데 새 존이 합류」가 **그 존의 첫 탭**(`tap_index=0`)으로 세어지고

있다」*가 **숫자로 확인됐다** — `retap_mode="once"` 쪽도 378건 움직인다.

⚠️ **1.88%를 「작으니 무시해도 된다」로 읽지 말 것** — 재탭 **번호**가 되돌아가는 것은
탭 수와 별개 축이고(위 §3 반례), `tap_index`는 재탭 정책이 소비하는 값이다.

  소관이다. 이 이슈는 **병합 경계·수명·후보 집합**까지다.
* ⚠️ **탐지 층의 수다** — 「탭 ±N%」가 「북 거래 ±N%」가 아니다(볼린저·체결·슬롯이 뒤에서
  또 깎는다). 손익 판정은 북에서만 낸다(WAN-341).
* ⚠️ **「엣지 없음」(WAN-84/88/111/114/124/151/201/248/386) 불변** — 이 이슈는 *존을 어떻게
  뭉치나*를 원본과 맞추는 것이지 *진입 규칙이 무작위와 구분되나*를 묻지 않는다.
* ⚠️ **차트 버그는 별개다** — 병합 시그널의 `zone_key`가 원본 단위 아카이브와 안 맞아 근거
  박스가 안 보이는 문제(WAN-149가 문서화한 알려진 한계). 측정에는 영향 없다.
