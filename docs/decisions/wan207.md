## §1 — 체결→처분(그리고 진입 알림) 간헐 유실: 원인은 스코프 버그였다

### 증상 (사용자 발견 2026-07-28)

`alphablock doctor`가 "처분 미기록 체결"(`status='filled'` + `entry_status IS NULL`)
**5건**을 잡았다. 45건 중 40건은 정상 기록(`entered`/`rejected`)이라 미배포·미재시작이
아니고, 러너도 죽지 않았다. id 41(LTC 1h)은 **진입·+1.5R 익절까지 확정인데 NULL**이었고,
진입/거부 텔레그램 알림도 안 오고 **익절 알림만** 도착했다.

### 근본 원인 — `order`는 `placed` 분기에서만 대입되는 지역 변수였다

`live/zone_limit_runner.py`의 `_handle_events`가 체결 이벤트를 처리하며 처분을
`order.journal_id`로 남겼는데, `order`는 **위쪽 `placed` 분기에서만** 대입되는
`_handle_events`의 지역 변수였다:

```python
for event in events:
    if event.kind == "placed":
        order = event.order          # ← 여기서만 대입
        ...
    elif event.kind == "filled" and event.fill is not None:
        report = self._executor.enter(...)   # 포지션이 먼저 열린다
        journal_id = order.journal_id        # ← 예약과 다른 배치면 order가 미대입
```

체결이 예약과 **같은 폴링 배치**에서 나면(가격이 존을 탭하는 그 1분봉 안에서 지정가까지
관통 — offset 2bp라 흔하다) 그 배치에 `placed`가 있어 `order`가 대입돼 정상 기록된다
(40/45). 그런데 주문이 걸린 뒤 **나중 폴링**에서 가격이 닿아 체결되면 그 배치엔 `placed`가
없어 `order`가 **미대입** → `enter()`가 포지션을 연 **직후** `UnboundLocalError`가 터진다.
그 예외는 폴링 루프의 시리즈별 `except`가 삼켜(러너는 안 죽고) 이후 청산만 정상 처리된다.
결과: **포지션은 열렸는데 `entry_status`는 NULL, 진입 알림도 유실**, 익절 알림만 온 거래.
이것이 WAN-194가 "쓰기 사이의 유실"로 부르던 바로 그 모양(`filled` + NULL)이라 손상 의심을
낳았지만, 실제로는 스코프 버그였다.

산발성도 설명된다: "나중 폴링에서 체결"은 소수(스치듯 닿지 않고 존에 얹혀 쉬다가 뒤늦게
관통한 주문)라 몇 시간에 한 건씩 NULL로 남는다.

### 수정

* **근본**: 체결 이벤트가 실어 온 주문(`event.order` — 그 주문 자신, `journal_id` 포함)을
  쓴다. `filled` 처리를 `_handle_fill(event)`로 분리했다.
* **belt-and-suspenders**: 진입 처리를 `try/finally`로 감싸 처분을 **반드시** 남긴다 —
  진입이 예외로 끊기면 최소한 사유를 붙인 `rejected`로 남겨 `filled` + NULL이라는 "진짜
  유실" 서명(WAN-194의 `orphan_fills`)을 오염시키지 않는다. 진입 알림도 자체 `try/except`로
  감싸 실패를 삼키지 않고 로그로 드러낸다(조용한 누락 금지, WAN-95/194 교훈).

### 완료 기준

* [x] 완료 거래는 **항상** `entry_status`를 갖는다 — 예약과 체결이 다른 폴링 배치인 경우
  회귀 테스트(`test_fill_on_later_poll_records_disposition`) + 예외 주입 테스트 2건
  (알림기 예외 · 진입 집행 예외)이 동작으로 고정한다.
* [x] 원인 1차 규명(이 문서).
* [x] 기존 NULL 5건은 **판별 불가라 백필 대상 아님** — `orphan_fills(since_ms=...)` /
  `doctor --orphans-since`로 도입 이후만 봐야 한다(열 도입 전 기록도 전부 NULL이므로).

§1은 성과·잔고엔 영향이 없다(그 둘은 `paper_trades`·지갑에서 나온다) — 장부 위생·관측성
이슈다. 손절폭 가드(0.3%)는 손대지 않았다.

## §2 — "전체 성과" total_return이 전액배팅이라 지갑·백테스트와 어긋났다

### 무엇이 문제였나 (사용자 발견 2026-07-28)

대시보드 "전체 성과"가 −0.95%인데 실제 잔고는 +($10,031)라 어긋났다. `paper/performance.py`가
자본곡선을 **매 거래에 자본 100%를 넣었다고 치고**(전액배팅) `net_pct`를 복리로 누적했다:

```python
equity *= 1.0 + s.net_pct / 100.0   # net_pct = 수량 무관 가격 이동 %
```

그런데 백테스트도 실제 페이퍼 지갑도 `risk_per_trade`(1%)로 사이징하고 레버리지 상한에
clamp된다 — 이 패널만 사이징을 무시해 자가 달랐다.

### 결정 (사용자 2026-07-28): 전액배팅 제거 → 지갑 기준

### 수정 — 두 부분이 얽혀 있다

전액배팅을 리스크-사이징으로 바꾸는 것만으로는 부족하다. **좁은 존(존폭 필터 1.28)은
손절이 가까워 레버리지 상한이 자주 binding**하므로, `r_multiple × risk_per_trade` 복리로도
실제 지갑과 어긋난다(그 근사는 clamp된 거래를 과대평가한다). 그래서 청산 시 실제 지갑에서
집계한 **달러 금액을 영속화**해 정확한 곡선을 재구성한다 — §2 본체와 "얼마 들어갔는지"
표시 요구가 같은 데이터에 물려 있다.

* **스키마**(`paper_trades`, idempotent `ALTER`): `quantity`·`notional`·`risk_amount`·
  `realized_pnl`·`equity_after` 5열 추가(옛 행은 판별 불가라 NULL). `live/executor.py`의
  청산 경로가 엔진이 정산한 실현손익·수량·명목과 진입 때 저장한 리스크 금액·청산 직후
  자본을 함께 넘긴다(`TradeDollars`).
* **성과**(`paper/performance.py`): 총수익률·MDD를 전액배팅이 아니라 자본곡선으로 낸다 —
  **전체 성과**는 청산 직후 실제 자본(`equity_after`)을 청산시각 순으로 이어 붙여 러너
  실제 지갑과 **정확히 일치**(`wallet_basis`, 초기 자본 `settings.paper_equity` 기준).
  **시리즈별**은 지갑이 격리되지 않으므로 `r_multiple × risk_per_trade` 복리로 정규화한다.
  달러 데이터가 없는 옛 행만 있으면 전체 성과도 이 정규화 곡선으로 폴백한다.
* **표시**(`paper/report.py`·`dashboard/app.py`): 거래 원장·CSV에 투입 명목·리스크·달러
  손익 열, 전체 성과에 총 투입/총 리스크/총 달러 손익 요약.

⚠️ **부수효과(좋음)**: 지금까지 전액배팅(페이퍼) vs 리스크-사이징(백테스트)이라 패리티가
오도했는데, 정정하면 apples-to-apples가 된다.
