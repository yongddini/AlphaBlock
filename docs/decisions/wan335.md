# WAN-335 — `stop-width --with-backtest`가 캐시를 읽는다 · 좁히기가 양쪽에 걸린다

**성격**: 버그/성능 수정 + 도구. **엔진·전략·기본값·토대 불변**(`ConfluenceParams()`·
`LeverageBookParams()` 그대로) · DB에 아무것도 쓰지 않는다(WAN-194 원칙) ·
`ALPHABLOCK_LIVE_TRADING=false` 유지.

## 왜 열렸나

2026-08-19에 WAN-334(서버 몫)를 돌리다 **네 번 연속 포기**했다. 48칸 → 24칸 → 7칸 →
**4칸까지 좁혀도 안 끝났다**. 사용자 원문: *"이정도로 오래걸리면 안되는거 아니야?"* ·
*"안끝나는데 저것도?"*. 도구가 실사용 불가라 측정 이슈가 답을 못 냈다.

## §1 — 캐시를 안 읽고 있었다 (느림의 진짜 원인)

같은 산출물을 두 명령이 다르게 얻고 있었다:

| 명령 | 백테 셋업 출처 | 체감 |
| -- | -- | -- |
| `alphablock trades --day …` | `load_cached_day` → **디스크 캐시** | 즉시 |
| `stop-width --day … --with-backtest` | `backtest_setup_rows` → **매번 처음부터** | 수 분~ |

그런데 야간 크론이 담는 것(`persist_day` → `backtest_setup_by_cell`)이 **정확히**
`stop-width`가 필요로 하는 셋업 행이다 — WAN-297이 캐시 버전을 올려 담기는 행을 「청산
거래만」에서 「셋업 전부」로 넓힌 이유가 그것이었다. **디스크에 있는 걸 무시하고 다시
굽고 있었다.**

고친 것:

1. `--with-backtest`가 **캐시를 먼저 조회**하고 **미스인 칸만** 계산한다
   (`_stop_width_backtest_rows`). 미스는 좌표의 데카르트 곱이 아니라 임의의 부분집합이라
   (칸마다 지문이 따로다) 칸 낱개 경로 `backtest_setup_by_cells`를 새로 냈다 —
   `backtest_setup_by_cell`이 그 위의 얇은 래퍼가 되므로 **다른 계산이 아니다**(회귀
   테스트가 두 경로의 셀 작업 목록으로 고정).
2. 🚨 **옛 엔진 판(stale)은 기본 거부**다. `trades`의 `--no-stale`과 **반대로** 엄격이
   기본이고 완화가 `--allow-stale`이다 — 이건 파리티 측정이라 엔진이 다른 두 판을 빼면
   「집행 차이」가 아니라 **「엔진이 바뀐 몫」**이 섞인다(WAN-325가 3열 대조를 끄는 것과 같은
   이유). 옵트인했을 때는 옛 판을 읽되 **미스를 계산으로 메우지 않는다**(그러면 한 표에 두
   엔진이 섞인다) — 그 사실을 화면이 밝힌다.
3. **몇 칸을 계산하는지 먼저 찍는다**(`캐시 적중 N/M칸 · 미스 K칸을 지금 계산합니다`).
   진행이 안 보여 「멈춘 건지 도는 건지」를 알 수 없었던 것이 실사용 중단의 절반이었다.
4. 캐시 지문에 워밍업이 들어가므로 `--warmup-days`가 기본값과 다르면 **전 칸이 당연히
   미스**다 — 조용히 느려지지 않게 화면이 밝힌다. 📌 **두 기본값은 실제로 같다**(캐시의
   `cell_fingerprint`도 `backtest_setup_by_cell(s)`도 `None` → `DEFAULT_WARMUP_DAYS`) —
   이슈가 「확인 필요」로 남긴 자리의 답이다.
5. `--recompute`(캐시 무시)를 남겼다 — 옛 동작이 그대로 도달 가능해야 두 경로의 결과가
   같은지 실제로 대조할 수 있다(완료 기준 5, 회귀 테스트가 렌더 본문 동등성으로 고정).

⚠️ **적재는 하지 않는다** — `stop-width`는 순수 조회다. 캐시를 채우는 것은
`alphablock trades --persist-cache`(야간 크론)의 일이다.

## 🚨 §1에서 드러난 진짜 결함 — 캐시가 조인 키를 버리고 있었다

캐시 경로를 켜자마자 **조인이 0건**이 됐다. 원인은 성능이 아니라 **행 스키마**였다:
WAN-297이 담기는 것을 셋업 행으로 넓히면서 payload는 넓혔는데 `timeline_cache_rows`의 열은
**거래 행 시절 그대로**라(「백테 행은 예약·목표가·손절 칸이 없다」는 당시엔 참인 전제)
왕복에서 다섯 칸이 통째로 사라졌다:

`reserve_ms`(탭 봉 시각) · `limit_price` · `stop_price` · `take_profit_price` · `tap_index`

하필 **`tap_index`는 조인 키의 일부**(`live.setup_compare.setup_key`)이고 **`stop_price`는
손절폭 그 자체**라, 캐시에서 읽은 행으로는 파리티 비교가 성립 자체를 안 했다. 화면에는
「짝 0건」만 떴을 것이다 — WAN-333이 고친 것과 **글자 그대로 같은 증상**이고 원인만 다르다.

고친 것: 열 다섯을 넓히고(ALTER 마이그레이션 포함) 열 순서를 `_ROW_COLUMNS` **한 곳**에서만
읽게 했다(INSERT·SELECT를 두 벌로 적으면 열을 늘릴 때 한쪽만 고쳐 값이 옆 칸에 들어간다 —
이 결함의 이웃한 실패 모드다). 왕복 무손실은 **행 전체 동등성**으로 고정한다(필드를 하나씩
세지 않는다 — 나중에 칸이 늘어도 함께 걸려야 한다).

📌 **캐시 버전 `wan297.1` → `wan335.1`** — 행의 의미가 바뀌었으므로 규약대로 올린다. 옛
적재분은 **지문이 갈라져 자동 미스**이고 **지워지지 않는다**. 배포 뒤 한 번 되채워야 한다
(`trades --persist-cache --days N`, 런북 참고). 옛 버전 셀은 옛 엔진 판 **폴백 후보에서도
빠진다**(WAN-325 §캐시 버전 — 행의 의미가 다른 판을 「옛 엔진 결과」라며 내주면 미체결·건너뜀
행이 빠진 표가 「계산됨」으로 뜬다).

## §2 — 좁히기가 백테 쪽에만 걸렸다

`--symbol`/`--tf`가 `backtest_setup_rows`에만 들어가고 `live_timeline_rows`에는 안 들어가,
`--symbol BTC/USDT:USDT --tf 15m`으로 돌리면 인구조사가 이렇게 찍혔다:

```
조인 인구조사: 라이브 셋업 60건(키 있음 59) · 백테 셋업 3건(키 있음 3)
  → 짝지어짐 3 · 짝 없음 라이브 57 · 백테 0
```

**라이브 60건은 그날 48칸 전부이고 백테 3건은 한 칸**이다. 하필 그 줄이 WAN-333이 「배선
오류를 지목하려고」 넣은 것이라 **정상 좁히기가 고장처럼 읽혔고**, PM이 실제로
「백테가 20배 적게 본다」는 판정을 WAN-334에 기록했다가 다음 실행에서 스스로 정정했다.

**(a)와 (b)를 둘 다 했다**: 좁히기를 라이브 쪽에도 걸고(조인 표에 다른 칸 라이브 행이 섞일
이유가 없다), 인구조사가 **분모도 밝힌다**(`라이브 셋업 1건(창 전체 2건 중 이 좌표)`).

📌 **§3(라이브 체결 분포)은 일부러 창 전체를 본다 — 의도된 비대칭이다.** 좁힌 TF를 주고도
그날 체결이 어느 TF에 있었는지가 보이는 성질이 실사용에서 유용했다(`--tf 15m`을 줬는데 §3이
1h까지 보여줘 체결이 두 TF에만 있음을 알았다). 그래서 좁히기는 **§1(조인)에만** 걸고, 좁혀
돌렸을 때 §3 머리에 그 사실을 찍는다(안 밝히면 다음 사람이 §3을 좁힌 표로 읽는다).

151/201) 불변** — 이 이슈는 도구가 답을 낼 수 있게만 했다.
